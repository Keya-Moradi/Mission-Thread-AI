# Decisions

Format: Date · Decision · Why · Alternatives considered.

## 2026-07-17 — Node 24.x pinned as target LTS

Why: Active LTS with the longest remaining support window as of this date (Active until Oct 2026, Maintenance until Apr 2028). Node 25 (odd majors never receive LTS status) is already end-of-life as of this writing and must not be used for development or builds.
Alternatives: Node 22 (Maintenance LTS already, shorter remaining active window).

## 2026-07-17 — Prisma schema centralized in packages/core

Why: the deterministic services (`getImpactedRequirements`, `calculateBudgetExposure`, etc.) and the future read-only MCP server both need direct DB access via `packages/core`; one schema avoids drift between two copies.
Alternatives: schema in `apps/web/prisma` (rejected — would force `packages/mcp-server` to depend on `apps/web`).

## 2026-07-17 — Three Prisma model merges approved for MVP

`TestResult` → `TestCase`, `SupplierUpdate` → `ProgramEvent`, `Approval` → `Decision`. Net model count 23 → 20.
Why: user requested junior-dev-level MVP complexity; each merged pair had no independent lifecycle need within MVP scope (no test run history, only one event type in MVP, approval and decision are always created 1:1 together). `AuditEvent` stays separate in all three cases as the append-only log entry.
Alternatives: build all 23 models exactly as listed in `SPEC.md` §6 (available later if a real need for the split emerges — e.g. a second event type would justify splitting `SupplierUpdate` back out of `ProgramEvent`).
Status: approved by user during Phase 0 plan review.

## 2026-07-18 — Prisma Client generator: `prisma-client-js` (not the newer `prisma-client` provider)

Why: Prisma 7 introduced a new `prisma-client` generator that emits raw TypeScript into a custom `output` path instead of compiled JS into `node_modules`. That raw-TS output uses `.js`-suffixed relative imports pointing at `.ts` files (standard TS `NodeNext` convention) — Turbopack (Next 16's dev/build bundler) could not resolve those specifiers when the package was loaded through `transpilePackages`, producing `Module not found` errors even inside Prisma's own generated files. Switching to the classic (now-deprecated-but-supported) `prisma-client-js` provider generates real compiled JS into `node_modules/@prisma/client`, which Next resolves through normal node_modules resolution with no special handling needed.
Consequence: `packages/core` imports `PrismaClient` from `"@prisma/client"` rather than a local generated path. Prisma 7 still required removing the schema's `datasource.url` in favor of `prisma.config.ts` + a driver adapter (`@prisma/adapter-pg`) regardless of generator choice — that part is unrelated to this decision.
Alternatives: keep `prisma-client` with custom `output` (rejected — broke Turbopack resolution, verified by reproducing the failure with `npm run dev`); patch Turbopack's `resolveExtensions`/`resolveAlias` (rejected — those options don't remap an explicit `.js` specifier to an existing `.ts` file, verified against Next's own docs).

## 2026-07-18 — `next-auth` pinned to the v5 beta channel

Why: Auth.js's own current documentation recommends `next-auth` v5 for Next.js App Router support; v4 predates the App Router pattern used here (Credentials provider, `auth()` in server components, Server Action sign-in). As of this date, `next-auth@latest` on npm still resolves to the v4 line (`4.24.14`); v5 (`5.0.0-beta.31`) is only available under the `beta` dist-tag.
Consequence: this is a pre-1.0 dependency and could introduce breaking changes on a version bump. Documented as a known risk in `README.md`.
Alternatives: use v4 with a Pages-Router-style compatibility shim (rejected — not the officially documented App Router path, more fragile long-term).

## 2026-07-18 — No Next.js middleware/proxy for authentication in Phase 1

Why: the revised Phase 1 instructions require not importing Prisma or `node:crypto` into middleware, and verifying Auth.js's current split-config pattern before adding middleware at all. Auth checks are done with `auth()` directly inside server layouts, pages, and the login Server Action instead.
Consequence: there is no session-refresh-on-every-request behavior that middleware would normally provide; acceptable for Phase 1's scope (no mutations exist yet). Revisit if/when a route genuinely needs edge-level gating.
Alternatives: add `proxy.ts` (Next 16's replacement name for `middleware.ts`) now (rejected — adds Edge-runtime constraints and a second auth config surface before there's a concrete need).

## 2026-07-18 — `apps/web/.env` is a symlink to the repo-root `.env`

Why: `SPEC.md` §17 requires `.env.example`/`.env.test.example` at the repo root, but Next.js only auto-loads `.env`/`.env.local` from the Next app's own directory (`apps/web/`), not the monorepo root. A symlink keeps one canonical `.env` file instead of duplicating secrets.
Consequence: a fresh clone must run `ln -s ../../.env apps/web/.env` once after copying `.env.example` — documented in `README.md`. The symlink itself isn't committed (it's local machine state, and `.env` is gitignored).
Alternatives: duplicate `.env` into `apps/web/` (rejected — two copies of the same secrets drift silently); configure Next to read a custom env path (rejected — not a standard, documented Next.js option).

## 2026-07-18 — Accepted 3 moderate `npm audit` advisories rather than force-fixing

Why: `npm audit fix --force` would downgrade `prisma` to `6.19.3` and `next` to a `9.x` canary to resolve advisories in nested/optional dev-tooling dependencies (`@prisma/dev`'s use of an old `@hono/node-server`, and a `postcss` copy bundled inside Next itself). Both advisories are in code paths this app doesn't exercise (an optional Prisma dev-studio dependency; Next's internal CSS stringification). Downgrading two major framework versions is a materially worse trade than the advisories themselves.
Consequence: `npm audit` will report 3 moderate findings until upstream ships non-breaking patches. Documented in `README.md` Limitations.
Alternatives: force-fix now (rejected — breaking downgrade); ignore silently (rejected — documented instead, per the project's own rule to record risks honestly).

## 2026-07-18 — Destructive-operation authorization policy

- Every destructive database invocation requires fresh human authorization.
- Approval applies only to the named command and target database.
- Previous approval must not be reused for a later destructive invocation.
- Third-party safety controls must never be bypassed or fabricated.
- The application's own allowlists and guards (`packages/core/src/db-safety.ts`) remain required even when external tooling also provides safety controls.

Why: destructive database commands (schema reset, full-table clear-and-reseed) are irreversible against whatever they target. Authorization has to be re-established per invocation, not carried forward from an earlier one, or "approval" stops meaning anything.
How to apply: this governs every destructive command in this repository going forward, regardless of which tool or terminal runs it.

## 2026-07-18 (correction pass) — Hardened `verifyPassword` against a malformed-hash authentication bypass

Confirmed as a real, reproducible defect: `Buffer.from(str, "hex")` silently stops decoding at the first invalid character instead of throwing, so a corrupted stored hash (bad migration, manual edit, future bug) with non-hex salt/hash fields could decode to two empty buffers. `scryptSync` happily derives a 0-byte key from a 0-byte salt, and `timingSafeEqual` on two empty buffers returns `true` — authenticating **any** password against that row. Reproduced directly in Node before fixing: `verifyPassword("literally anything", "scrypt:16384:8:1:zz:zz")` returned `true`.
Fix: `packages/core/src/auth/password.ts` now fully validates every field (exact marker, field count, integer-only cost params in bounds, power-of-two N, a combined `128*N*r` memory ceiling, even-length hex within a plausible byte-length range) before any bytes are ever passed to scrypt, and wraps the scrypt call itself in try/catch so any unanticipated error fails closed instead of throwing out of an auth check.
Async decision: switched `hashPassword`/`verifyPassword` from `scryptSync`/`timingSafeEqual`-only to `crypto.scrypt` (promisified) so a slow verify (intentionally CPU/memory-heavy by design) never blocks Node's single event loop thread during a login attempt. This was straightforward here since the only caller (`apps/web/src/auth.ts`'s `authorize()`) was already async.
Alternatives: keep the length checks tied exactly to the current `SALT_LENGTH`/`KEY_LENGTH` constants (rejected — would break verification of any hash created under different future parameters; used a safe range instead, matching the format's own stated goal of tolerating parameter changes).

## 2026-07-18 (correction pass) — Shared destructive-database-operation guard

**Superseded by the 2026-07-18 second correction pass ("Exact (host, port, database) target tuples...", "Destructive commands renamed...") and the 2026-07-18 third correction pass ("Exact GitHub Actions target requirement", "Target-specific destructive seed commands") below.** The independent host/database-name allowlists, the permanently-enabled example-file flag, the `db:seed`/`db:seed:destructive` command names, and the `CI=true` check described in this entry no longer reflect current behavior — kept here as the historical record of the original fix, not as a description of the present design.

`packages/core/src/db-safety.ts`'s `isTestDatabaseName` used `.includes("test")`, a plain substring match that would also match `contest_prod`, `latest`, `attestation`, and `testament`. It also had no allowlist, no production/host checks, and — critically — the seed script's `clearExistingData()` (which wipes every table) had **no guard of any kind**, running unconditionally on every `npm run db:seed`. Separately, one error path in the old `reset-test-db.ts` interpolated the raw `TEST_DATABASE_URL` (including credentials) directly into a `console.error` call.
Fix: replaced the substring check with a token-boundary regex (`test` must be delimited by the string start/end or `_`/`-`) plus an explicit `APPROVED_TEST_DATABASE_NAMES`/`APPROVED_DEV_DATABASE_NAMES` allowlist, and added one shared `checkDestructiveOperationAllowed()` guard used by both `reset-test-db.ts` and `seed.ts`'s clear step. It fails closed on: `NODE_ENV=production`, a missing/malformed URL, a host outside `APPROVED_LOCAL_HOSTS` (localhost/127.0.0.1/::1/postgres — no remote-host opt-in exists, since nothing in this project legitimately needs one yet), a database name outside the operation's specific allowlist, or a missing `ALLOW_DESTRUCTIVE_DATABASE_OPERATION=true` opt-in (exact-match only — "1"/"yes"/"TRUE" do not count). All returned messages are pre-sanitized to host/port/database only; the raw connection string is never logged.
Consequence: `npm run db:seed` now requires `ALLOW_DESTRUCTIVE_DATABASE_OPERATION=true` in the environment — added to `.env.example`/`.env.test.example` (and CI) so local/CI workflows are unaffected, but a misconfigured `DATABASE_URL` without that flag (or pointed at an unrecognized host/name) now fails safely instead of silently wiping data.
Alternatives: keep the two scripts' checks independent (rejected — that's exactly how the seed script ended up with no check at all); let the flag alone gate remote hosts too (rejected — kept the host allowlist unconditional for a stronger guarantee, since no real use case needs an override today).

## 2026-07-18 (correction pass) — Deterministic IDs for all seeded rows; distinct password hash per demo user

`User` and `Dependency` were the only seeded models still using Prisma's `@default(cuid())` instead of a fixed ID, and all three demo users shared a single `hashPassword()` call — meaning identical salts across all three rows, which defeats salting's purpose (one cracked hash exposes all three) and isn't representative of how real user rows are ever created.
Fix: added `DEMO_USER_IDS` (`USER-PM`, `USER-ENG-LEAD`, `USER-EXEC`) and `DEPENDENCY_IDS` (`DEP-001`..`DEP-008`) to `packages/core/src/seed/ids.ts`; `prisma/seed.ts` now calls `hashPassword()` once per user and passes explicit `id` values for both models. No schema change was needed — `@default(cuid())` still applies for any future non-seeded row, seed data just always supplies its own ID.

## 2026-07-18 (correction pass) — RecordType: one Prisma enum plus three Zod allowlists, not three Prisma enums

`RecordType` was reused as-is across three different contexts (evidence citations, proposed-change targets, audit targets) with no restriction preventing, say, a `ProposedChange` from targeting a `Supplier`. It also had no `DEPENDENCY` entry and no way to represent an audit event about a workflow record (an `ImpactAnalysis` starting, a `Decision` being recorded).
Decision: expanded `RecordType` to a full superset (added `DEPENDENCY`, `IMPACT_ANALYSIS`, `MITIGATION_OPTION`, `PROPOSED_CHANGE`, `DECISION`, `SOURCE_REFERENCE`), and added `packages/core/src/record-types.ts` with three Zod allowlists — `evidenceRecordTypeSchema` (domain records only), `proposedChangeTargetTypeSchema` (`MILESTONE`/`RISK`/`BUDGET_ITEM` only, matching `ProposedChangeType`), `auditTargetTypeSchema` (the full superset) — that Phase 4/5 application code must validate against when creating these rows.
Why one enum + Zod over three separate Prisma enums: Prisma has no native "enum subset" constraint either way, so per-context enforcement always happens at the application boundary regardless of which schema shape is chosen. Three near-identical Prisma enums would need to be kept in sync by hand (e.g. `PROGRAM_EVENT` belongs in both the evidence and audit sets but not the change-target set) — one source of truth plus explicit allowlists was judged less error-prone for an MVP, at the cost of the database itself not enforcing the restriction (only the application layer does, once Phase 4/5 wires these schemas into the actual create paths — they exist now but are not yet called from anywhere, since no code creates these rows yet).
Also added in the same migration: a `SourceReference` uniqueness constraint on `(impactAnalysisId, recordType, recordId)` (the same record must never be double-cited as evidence for one analysis) and a `Decision.traceId` index.
Migration: `20260718055852_expand_record_type_and_add_constraints`, applied to both `missionthread_dev` and `missionthread_test`.

## 2026-07-18 (correction pass) — ImpactAnalysis attempt lifecycle

Documenting the existing schema design rather than changing it: one `ImpactAnalysis` row represents one provider attempt for one program event. `ProgramEvent` has a one-to-many relation to `ImpactAnalysis` (re-analysis creates a new row), and each row carries its own `attempt` number, `traceId`, `status`, and duration/validation metadata. The "exactly one retry" rule (SPEC.md §10) is implemented by the Phase 4 orchestration code creating at most two `ImpactAnalysis` rows per triggering call (attempt 1, then attempt 2 only on failure) — not by a separate attempts table or by mutating one row in place, which would lose the failed attempt's own record. This satisfies SPEC.md §16's observability requirements (trace ID, attempt number, duration, safe error category are all columns on this same row) without introducing a second model before Phase 4 exists to populate it.

## 2026-07-18 (correction pass) — Dockerfile repaired: Next.js standalone output, non-secret build-time DATABASE_URL

The original Dockerfile's build stage ran `prisma generate` with no `DATABASE_URL` at all — `packages/core/prisma.config.ts` reads it eagerly, so this failed immediately. Its runtime stage also ran `npm run start --workspace @missionthread/web` without ever copying the root `package.json`, which npm workspace commands require.
Fix: enabled `output: "standalone"` and set `outputFileTracingRoot` to the monorepo root in `apps/web/next.config.ts` (verified via Next's own docs — monorepo tracing defaults to the app's own directory and would otherwise miss the `@missionthread/core` workspace package). The build stage now sets a clearly non-secret, unreachable placeholder `DATABASE_URL` build arg (`postgresql://build:build@localhost:5432/build_placeholder`) — sufficient because `prisma generate` never opens a connection — and the runtime stage runs `node apps/web/server.js` directly against the traced, pruned `.next/standalone` bundle, which needs no `npm`/workspace command and therefore no root `package.json` at runtime at all. Also discovered and defended against: Next's standalone output additionally copies any `.env` file it finds on disk at build time into the bundle; `.dockerignore` already excludes `.env` from the build context, and an explicit `rm -f` after the build step is a second layer of defense against that specific behavior. Runs as a non-root `nextjs` user.
Verified live: `docker build` succeeded; a container from the image started; `GET /login` returned 200 with the expected sign-in form; `GET /` correctly redirected unauthenticated; container was stopped and the test image removed afterward. Noted for real deployments (not needed for this local verification): Auth.js v5 logs an `UntrustedHost` warning when the request's `Host` header doesn't match its trusted-host configuration — a real deployment needs `AUTH_TRUST_HOST=true` or an explicit `AUTH_URL` set via the orchestrator's runtime environment, not baked into the image.
Alternatives: remove the Dockerfile and defer entirely to Phase 8 (rejected — SPEC.md §17 lists `Dockerfile` as a required Phase 1 file, and the standalone-output fix was achievable and verifiable now).

## 2026-07-18 (second correction pass) — Exact (host, port, database) target tuples replace independent host/database allowlists

The previous guard checked host and database name independently, so it never validated the port at all — `localhost:5432/missionthread_dev` (a developer's _other_ local Postgres, not this project's Docker Compose instance on 55432) would have passed. Replaced `APPROVED_LOCAL_HOSTS` + `APPROVED_DEV_DATABASE_NAMES` + `APPROVED_TEST_DATABASE_NAMES` with a single `ApprovedDatabaseTarget` tuple type (`{ host, port, database, requiresCi? }`) and three fixed tuple lists: `LOCAL_DEV_TARGETS` (`localhost`/`127.0.0.1` : `55432` / `missionthread_dev`), `LOCAL_TEST_TARGETS` (same hosts/port / `missionthread_test`), and `CI_TEST_TARGETS` (`localhost` : `5432` / `missionthread_test`, `requiresCi: true`). `findApprovedDatabaseTarget()` requires every field to match exactly; callers pass only the subset of tuples relevant to that operation (e.g. `reset-test-db.ts` only ever sees `LOCAL_TEST_TARGETS`, never the dev tuples).
CI detection: `requiresCi: true` tuples only match when `process.env.CI === "true"` (exact string match, same discipline as the opt-in flag) — GitHub Actions sets this automatically for every job, so nothing has to set it explicitly in `.github/workflows/ci.yml`.
IPv6: intentionally not supported. Verified directly in Node that `new URL("postgresql://x@[::1]:5432/db").hostname` returns the bracketed literal `"[::1]"`, not `"::1"` — the previous `APPROVED_LOCAL_HOSTS` list contained the unbracketed form, which could never actually have matched a real parsed URL. Rather than fix that mismatch, IPv6 was dropped entirely: nothing in this project's Docker Compose config, CI workflow, or local tooling connects over IPv6, so adding it now would be untested surface with no real use case. A bracketed `"[::1]"` tuple can be added later if a genuine need appears.
Compose-internal host removed: the previous `APPROVED_LOCAL_HOSTS` included `"postgres"` (the Docker Compose service's in-network hostname) on the theory that a future containerized app service might use it. `docker-compose.yml` currently defines only the `postgres` service itself — no web application service exists that would ever resolve that hostname — so this was a dead allowlist entry. Removed; will be reintroduced if a real containerized runtime path is added (e.g. in Phase 8).
Migration: none required — this is an application-layer (Zod/TypeScript) change, not a schema change.

## 2026-07-18 (second correction pass) — Destructive commands renamed to make intent explicit at invocation, and the opt-in flag is never permanently enabled

The example env files previously shipped `ALLOW_DESTRUCTIVE_DATABASE_OPERATION=true` as enabled configuration, described as "safe to leave set" — which defeats the point of requiring an explicit opt-in, since it would never actually be off. Removed the flag from `.env.example` and `.env.test.example` entirely.
In its place: `packages/core`'s scripts were renamed to `db:seed:internal` and `db:reset:test:internal` (not meant to be run directly), and the root `package.json` gained `db:seed:destructive` and `db:reset:test`, both of which set the opt-in flag only for their own child process via a new `scripts/with-destructive-auth.mjs` wrapper. The wrapper uses `child_process.spawn()` with an explicit `env` object rather than shell `VAR=value cmd` syntax, so the same command works on Windows (where `cmd.exe` doesn't support that syntax) without adding a `cross-env`-style dependency. CI's "Seed CI test database" step now calls `npm run db:seed:destructive` — the flag is no longer set at the workflow-wide `env:` level.
Naming: avoided a root script and a workspace script sharing the exact same name (the previous `db:reset:test` at both levels was ambiguous about which one actually ran) — the workspace-level scripts now carry an explicit `:internal` suffix.
Alternatives: keep the flag permanently enabled in example files (rejected — the explicit finding this pass); add a `cross-env` dependency for shell-syntax portability (rejected — a ~20-line wrapper needed no new dependency).

## 2026-07-18 (second correction pass) — Deferred: `ProposedChangeType.NEW_ACTION` target-field conflict

Not implemented this pass (Phase 5 work) — documented so the conflict isn't rediscovered from scratch. `ProposedChange.targetRecordId` and `targetRecordType` are currently non-nullable, but `ProposedChangeType.NEW_ACTION` describes creating a new action, not modifying an existing record — there is no existing target to reference, so a `NEW_ACTION` row would be forced to either fabricate a target or violate the non-null constraint.
Planned Phase 5 solution: make `targetRecordId` and `targetRecordType` nullable in the schema; validate `ProposedChange` creation with a Zod discriminated union keyed by `changeType` — `MILESTONE_DATE`/`RISK_UPDATE`/`BUDGET_UPDATE` require both target fields (validated against `proposedChangeTargetTypeSchema`), `NEW_ACTION` forbids them, unless a future revision explicitly models actions as belonging to an existing parent record. Never fabricate a placeholder target ID to satisfy a non-null constraint.
No schema or migration change made now — `SPEC.md` does not require this before Phase 2, and implementing it without the Phase 5 workflow code that would actually create these rows risks guessing the wrong shape.

## 2026-07-18 (second correction pass) — Deferred: `ImpactAnalysis` retry-pair grouping key

Not implemented this pass (Phase 4 work). The existing one-row-per-attempt design (see the 2026-07-18 correction-pass entry above) correctly persists each attempt as its own row, but has no stable key linking attempt 1 and attempt 2 of the _same_ retry sequence together, distinct from a later, separate re-analysis of the same event.
Planned Phase 4 solution: add an `analysisRunId` column with a uniqueness rule equivalent to `(analysisRunId, attempt)`. Attempt 1 and its retry (attempt 2) share one `analysisRunId`; a later, independent re-analysis of the same `ProgramEvent` gets a new `analysisRunId`. This keeps failed attempts individually persisted (SPEC.md §10's "persist a failed analysis attempt" requirement) while making "the two attempts that belong together" a queryable fact instead of an inferred one.
Not creating a separate `AnalysisAttempt` model unless Phase 4 implementation proves `analysisRunId` insufficient — SPEC.md's own guidance is to avoid a new model unless it adds real value beyond what a grouping key provides.
No schema or migration change made now, for the same reason as the `NEW_ACTION` entry above.

## 2026-07-18 (third correction pass) — Exact GitHub Actions target requirement: `GITHUB_ACTIONS=true`, not `CI=true`

The second-pass CI target tuple authorized on `CI === "true"`. That's insufficient specifically for a _GitHub-Actions_-only target: `CI=true` is a loose convention many local shells, editor integrations, and other CI providers also set, so it can't uniquely identify "this is a GitHub Actions runner" the way `GITHUB_ACTIONS` (which only GitHub Actions sets) can.
Fix: renamed `ApprovedDatabaseTarget.requiresCi` → `requiresGitHubActions`, and `CI_TEST_TARGETS` → `GITHUB_ACTIONS_TEST_TARGETS`; `findApprovedDatabaseTarget()` now checks `env.GITHUB_ACTIONS === "true"` exclusively for that tuple — `CI` is not consulted at all, so `CI=true` alone (GitHub Actions absent) correctly fails, and `GITHUB_ACTIONS=true` alone (CI absent) correctly passes. 16 new/updated unit tests cover both variables independently, uppercase/whitespace variants of the value, and the dev-database-on-port-5432 and arbitrary-host/port negative cases.
Alternatives: require both `GITHUB_ACTIONS=true` and `CI=true` together (rejected — `GITHUB_ACTIONS` alone is already authoritative and sufficient; requiring both would only make the check more likely to fail in a legitimate GitHub Actions run if some future workflow change ever left `CI` unset for another reason).

## 2026-07-18 (third correction pass) — Target-specific destructive seed commands; explicit `MISSIONTHREAD_SEED_SCOPE`

`seed.ts`'s `clearExistingData()` previously accepted the union of `LOCAL_DEV_TARGETS`, `LOCAL_TEST_TARGETS`, and the GitHub Actions target all at once, and the single public command `db:seed:destructive` authorized whichever one `DATABASE_URL` happened to point at — every possible target was allowlisted, but the command name itself never said which database a user was actually authorizing.

## 2026-07-18 (fourth correction pass) — Seed scope validated before database configuration is loaded or Prisma is initialized

Previously, `seed.ts` validated `MISSIONTHREAD_SEED_SCOPE` inside `clearExistingData()`, which ran after the module had already loaded `.env`/`.env.test` via `dotenv` and already constructed a live `PrismaPg` adapter and `PrismaClient` against `DATABASE_URL`. An invalid or missing scope was still caught before any row was deleted, but only after database configuration had already been loaded and the Prisma adapter/client had already been constructed — an unnecessary sequencing gap for a check this cheap to run first. (Constructing `PrismaPg`/`PrismaClient` does not itself open a network connection — Prisma connects lazily on first query — so the prior ordering did not necessarily reach the database; the gap was in configuration/object construction happening before validation, not in an actual connection being opened.)

Consequence: an invalid `MISSIONTHREAD_SEED_SCOPE` now fails before this process loads database configuration or constructs the Prisma client, not merely before it deletes data — and the failure message never echoes back whatever was actually in the environment variable.
Alternatives: leave the check where it was, inside `clearExistingData()` (rejected — the fail-first ordering guarantee this pass is enforcing is that an unauthorized process never even reaches the point of configuring database access, not just the point of mutating data); keep printing the raw rejected value for debuggability (rejected — an environment variable that fails validation is, by definition, unexpected input, and treating it as safe to log is exactly the assumption that leads to credential leaks in error paths).

## 2026-07-18 (Phase 2) — Deterministic-service error strategy: one `ServiceResult<T>` union, never throw for expected failures

Why: `SPEC.md` §8 lists eleven public functions with heterogeneous failure modes (missing component, missing risk, invalid input array). Mixing thrown exceptions for some and return values for others would force every caller (Phase 3 UI, Phase 4 evidence builder) to remember which functions throw and which don't.
Decision: every function in `packages/core/src/analysis/` returns `ServiceResult<T> = { ok: true; data: T } | { ok: false; error: DomainError }` (`packages/core/src/analysis/types.ts`). `DomainError` has `code: "NOT_FOUND" | "VALIDATION_ERROR"`, an optional `entityType`/`entityId`, and a safe `message`. Raw Prisma errors are never returned to callers — `NOT_FOUND` is produced by an explicit existence check, not by catching a Prisma "record not found" exception. Input validation (`packages/core/src/analysis/schemas.ts`) runs before any database query and produces `VALIDATION_ERROR` the same way.
Alternatives: throw typed errors (rejected — forces try/catch at every call site for what are often expected, non-exceptional outcomes, e.g. "this component has no impacted requirements" vs. "this component doesn't exist" are both ordinary results, not exceptions); throw for NOT_FOUND but return a value for validation (rejected — the whole point is one consistent strategy).

## 2026-07-18 (Phase 2) — Input-ID validation: reject padding/whitespace/duplicates, never silently normalize

`entityIdSchema` (`packages/core/src/analysis/schemas.ts`) rejects an empty string, a whitespace-only string, and a string with leading/trailing whitespace — it does not trim-and-accept. Real seeded IDs (`COMP-EC440`, `REQ-001`, ...) never have surrounding whitespace; silently trimming a caller's malformed ID would hide a caller-side bug instead of surfacing it as a `VALIDATION_ERROR`.
For functions taking an ID array (`getVerificationGaps`, `getRelatedDefects`), the array schema additionally rejects duplicate entries outright (`VALIDATION_ERROR`), rather than silently deduplicating — a duplicate requirement ID would double-count that requirement in coverage ratios and gap lists, which is exactly the "distort results" case `PROJECT_GUIDE.md`'s Phase 2 instructions call out. An empty array is accepted (returns an empty result), since "analyze zero requirements" is a valid, non-malformed call.

## 2026-07-18 (Phase 2) — Dependency traversal direction: `fromMilestone` is upstream, `toMilestone` is downstream; both returned separately

The `Dependency` model's own schema comment says "from finishes before to starts." `getDependencyChain(milestoneId)` therefore treats `fromMilestoneId` edges as pointing to a **prerequisite** (upstream) and `toMilestoneId` edges as pointing to a **dependent** (downstream), and returns both as separate arrays (`upstream`, `downstream`) rather than picking one direction — a caller asking "what does this milestone depend on" and a caller asking "what depends on this milestone" both need an answer, and conflating them would lose information.
Cycle/duplicate protection is implemented in a pure, DB-free helper (`traverseDependencyChain()` in `packages/core/src/analysis/dependencies.ts`) that takes an in-memory edge list and a start ID: a `visited` set keyed by milestone ID stops traversal from ever revisiting a node (so a synthetic cycle terminates instead of looping), and a `visitedEdges` set keyed by `${from}->${to}` prevents a duplicate edge from producing a duplicate chain entry. The DB-backed `getDependencyChain()` fetches every `Dependency` row for the milestone's program in one query (not one query per hop — see the N+1 note below) and hands the resulting edge list to the pure helper. This also makes cycle protection unit-testable with a fabricated cyclic edge list, without needing to seed an actual cycle into Postgres.

## 2026-07-18 (Phase 2) — Schedule cascade assumption: a delay shifts every impacted milestone's planned date by the same day count

`calculateScheduleExposure(eventId)`'s `latestExposedDate` is computed as `max(milestone.plannedDate + directDelayDays)` across every impacted milestone (direct: milestones on the event's component; dependency-derived: downstream milestones reached via `getDependencyChain`'s downstream edges from each direct milestone). This is a deliberate simplification, not a claim that real schedule float/slack was modeled: the schema has no per-milestone float/buffer field, so a 1:1 "the whole delay propagates downstream unmitigated" assumption is the only value derivable without inventing data. This is recorded as an explicit assumption in `buildAnalysisEvidence()`'s `assumptions` list, not presented as a precise scheduling-engine result.
Date arithmetic uses UTC calendar days: seeded/stored dates are date-only values (`new Date("2026-09-15")`, parsed by JS as UTC midnight), so `Math.round((b.getTime() - a.getTime()) / 86_400_000)` gives an exact calendar-day count with no local-timezone drift, as long as both operands are UTC-midnight-aligned — true for every date this schema stores. `calculateScheduleExposure` also compares the event's stored `delayDays` against the value computed from `originalDate`/`revisedDate` and reports (does not silently swallow) any disagreement.

## 2026-07-18 (Phase 2) — Budget variance sign convention and mixed-currency handling

Sign convention: `varianceAmount = actualTotal - plannedTotal` throughout `calculateBudgetVariance`/`calculateBudgetExposure`. A positive value is a cost overrun (spent more than planned); negative is an underrun. All arithmetic uses `Prisma.Decimal` (re-exported from `@prisma/client`, backed by `decimal.js`), never plain JS `number` addition, so cents can't drift from binary floating-point rounding; totals are serialized as fixed-2-decimal strings (`"480000.00"`), not numbers, in the returned result.
`BudgetItem.currency` defaults to `"USD"` but isn't constrained to a single value program-wide. `calculateBudgetVariance` groups items by currency: if exactly one currency is present, the top-level `plannedTotal`/`actualTotal`/`varianceAmount`/`variancePercentage` are populated for it; if the program's budget items span more than one currency, those top-level fields are `null` (never a silently-wrong cross-currency sum) and a `byCurrency` breakdown array carries the same fields per currency instead. `variancePercentage` is `null` (not `Infinity`/`NaN`) whenever `plannedTotal` is exactly zero, with a note in `missingData`.

## 2026-07-18 (Phase 2) — Budget exposure cannot compute a new incremental delay cost; documents the schema gap instead of inventing one

`calculateBudgetExposure(eventId)` links the event to budget items only through `ProgramEvent.componentId -> BudgetItem.componentId` — the only deterministic link the schema provides. Neither `ProgramEvent` nor `BudgetItem` has a per-day or per-unit cost-impact field, so there is no way to deterministically compute "the dollar cost of this specific 28-day delay" — doing so would require inventing a number. Instead, `totalDeterministicExposure` is defined as the sum of `plannedAmount` across the directly-linked budget items (the total budget tied to the affected component, i.e. the amount actually at risk from schedule/cost pressure on that component), and `currentVarianceTotal` is the existing `actual - planned` variance already present on those same items (same sign convention as `calculateBudgetVariance`). `missingData` always includes an explicit note that no incremental delay-cost figure is calculable from current schema fields. This limitation is also carried into `buildAnalysisEvidence()`'s `unknowns` list.

## 2026-07-18 (Phase 2) — Risk score formula, band mapping, and a genuine seeded inconsistency (`RISK-003`)

Formula: `score = probability * impact` (both stored as `Int`, conventionally 1–5 in this dataset, giving a score range of 1–25). Band mapping: `1–4` → `LOW`, `5–9` → `MEDIUM`, `10–14` → `HIGH`, `15–25` → `CRITICAL`. `calculateRiskScore` reports the computed band alongside the stored `Risk.severity` and a `severityConsistent: boolean` — it never lets the stored text label silently override the numeric result.
Applying this mapping to the seed data surfaces a real, pre-existing inconsistency: `RISK-003` (`probability: 2, impact: 2` → score `4` → band `LOW`) is stored with `severity: MEDIUM`. This is not a bug introduced by Phase 2 — it's the kind of disagreement the spec explicitly asked this function to detect and report rather than paper over, and `db-safety.test.ts`-style regression coverage exists for exactly this case (`RISK-003` is asserted to come back `severityConsistent: false`). Probability/impact values outside the expected 1–5 range are not rejected (they're read from the database as-is) but are surfaced via a `warnings` array rather than silently accepted as normal.

## 2026-07-18 (Phase 2) — Readiness score: five equal-weighted, independently-documented factors, 0–100, missing data scored as neutral (100%) with a warning

`calculateReadinessScore(programId)` is `round(sum of five factors)`, each worth 20 points (100 total), each computed as `(healthyCount / totalCount) * 20`:

1. **Verification coverage** (20 pts): proportion of the program's requirements with zero verification gaps (every linked test `PASSED`, and at least one test exists) per `getVerificationGaps`.
2. **Test health** (20 pts): proportion of the program's test cases with `outcome: PASSED`.
3. **Milestone health** (20 pts): proportion of milestones whose `status` is not `AT_RISK` or `DELAYED`.
4. **Defect health** (20 pts): proportion of defects whose `status` is not `OPEN` or `IN_PROGRESS` (i.e. `RESOLVED`/`CLOSED` count as healthy).
5. **Risk health** (20 pts): `(1 - averageActiveRiskScore / 25) * 20`, where "active" risks are `status: OPEN` or `MITIGATING` (a `CLOSED` risk no longer counts against readiness) and `25` is the theoretical max `calculateRiskScore` (5×5), not just the observed max in the data — so the scale doesn't silently shift if worse risks are added later.

Missing-data policy: if a factor's denominator is zero (e.g. a program with no budget items, no tests, no risks), that factor scores its **full** 20 points (treated as neutral/healthy, not penalized for absent data) and a corresponding entry is added to the result's `warnings` array — this was chosen over redistributing the other factors' weights (extra complexity for a 5-factor MVP formula) or scoring it zero (would wrongly penalize a program for not yet having, say, any defects logged). Rounding: the total is rounded to the nearest integer (`Math.round`) and clamped to `[0, 100]`; factor subscores are reported unrounded in the breakdown so the total is reproducibly re-derivable from them.
Budget variance was deliberately **not** made a sixth factor: `calculateBudgetVariance` can return `null` totals under mixed currency, and folding a nullable input into a fixed 100-point formula would need its own missing-data special case on top of the general one above — deferred rather than guessed at for the MVP.

## 2026-07-18 (Phase 2) — Evidence bounding: `rawNotes` is never a `summary`; it's a separate, explicitly-labeled untrusted field

`buildAnalysisEvidence(eventId)`'s `evidence[]` array (the bounded allowlist an eventual Phase 4 AI call would receive) only ever contains `summary` text built from validated, structured fields (titles, statuses, dates, IDs) — **never** `ProgramEvent.rawNotes`, which is supplier-submitted, untrusted free text (the seeded `EVT-SUPPLIER-001` row deliberately contains a prompt-injection-style sentence — see `prisma/seed.ts`). Putting `rawNotes` into an evidence item's `summary` field would make it structurally indistinguishable from every other trusted, deterministically-derived summary once it reached a future prompt.
Instead, `buildAnalysisEvidence()`'s top-level result carries a separate `untrustedSupplierNotes: string | null` field, outside the `evidence[]` array and outside `EVIDENCE_RECORD_TYPES`, explicitly documented as data — never instructions — that Phase 4 must keep clearly isolated (e.g. wrapped and labeled in its own prompt section) and that no Phase 2 calculation ever reads. Evidence items are deduplicated by `recordType + recordId` and sorted by a fixed `EVIDENCE_RECORD_TYPES` order then by `recordId`, so evidence output is stable and reproducible across calls.

**Superseded by the 2026-07-18 (Phase 2 correction pass) entries below** — `untrustedSupplierNotes` was replaced by a two-field `untrustedText: { reason, rawNotes }`, since `event.reason` turned out to have the same untrusted-free-text problem and was still leaking into the trusted event summary. Kept here as the historical record of the original design.

## 2026-07-18 (Phase 2 correction pass) — `buildAnalysisEvidence` now returns the full structured deterministic analysis, not just source-reference summaries

## 2026-07-18 (Phase 2 correction pass) — Computed schedule data is authoritative in `eventFacts`; `event.reason` joins `rawNotes` as untrusted text

Confirmed as a real, reproducible defect (two related issues): (1) the previous evidence summary interpolated `event.delayDays` directly, presenting the _stored_ value as fact even on the (rare, but explicitly detected elsewhere in Phase 2) occasion it disagrees with the dates; (2) `event.reason` — free text a user enters when recording an event, no different in kind from `rawNotes` — was embedded directly into the trusted `PROGRAM_EVENT` evidence summary, while only `rawNotes` was treated as untrusted.

## 2026-07-18 (Phase 2 correction pass) — Explicit, documented evidence bounds

Not a defect in existing behavior (the seeded data never came close to any reasonable limit), but a real gap: nothing in `buildAnalysisEvidence()` bounded the size of what it returned, which the task correctly identified as unsafe to leave unbounded before this evidence could ever be handed to a model (Phase 4).
Limits (`EVIDENCE_LIMITS` in `packages/core/src/analysis/evidence.ts`): 100 maximum total evidence items, 25 maximum items per record type, 500-character maximum evidence-item summary length, 4,000-character maximum length per untrusted-text field (`reason`, `rawNotes` independently). Applied in `applyEvidenceBounds()` (item limits, pure and exported) and `truncateText()`/`truncateUntrustedField` (length limits, pure and exported): summaries are truncated first, then the per-record-type cap, then the overall cap — each preserving the existing deterministic order (`EVIDENCE_RECORD_TYPES` order, then `recordId`) rather than re-sorting, and each producing an `unknowns` entry rather than a silent drop. `truncateText()` is surrogate-pair-safe: it never cuts a UTF-16 astral character (e.g. an emoji) in half, checking whether the code unit immediately before the cut point is an unpaired high surrogate and backing up one further position if so.
Alternatives: add a token-counting/tokenizer dependency now to bound by estimated model tokens instead of character/item counts (rejected — the task explicitly defers this past Phase 2; character and item counts are simple, dependency-free, and already meaningfully bound the payload); silently drop overflow without a note (rejected — indistinguishable from "there was nothing more to report," which is a materially different and more dangerous claim for an evidence set headed toward a model).

## 2026-07-18 (Phase 3) — Fixed a real CI blocker: the smoke test could hang for GitHub's full 6-hour job timeout

Confirmed as a real, reproducible defect, discovered while verifying CI was green before starting Phase 3: the smoke-test step of the immediately preceding push (`e7096d1`) never completed — GitHub Actions job history showed several earlier pushes auto-cancelled after exactly 6 hours (GitHub's default job timeout), each apparently stuck at the same step, with no failure signal at all in between.

## 2026-07-18 (Phase 3) — Event-entry contract: a strict Zod discriminated union, server-computed `delayDays`

`packages/core/src/events/schemas.ts` defines `eventEntrySchema`, keyed by `eventType` (`SUPPLIER_DELAY` | `GENERAL_UPDATE`), each branch `.strict()` (rejects unknown fields, including a client-supplied `delayDays` — which was never part of the contract in the first place, not merely rejected after the fact). Dates use a custom `dateOnlySchema`: a `YYYY-MM-DD` format check plus a round-trip `Date.UTC(...)` calendar-validity check, so `"2026-02-30"` (matches the format regex but isn't a real date) is rejected. `delayDays` itself is computed server-side in `recordProgramEvent()` via the same `utcDayDifference()` already used by `calculateScheduleExposure()` (Phase 2) — one shared UTC-day-arithmetic implementation, not two.
Bounds: `MAX_QUANTITY = 100_000` (arbitrary but documented — large enough for any real lot size, small enough to catch an obviously-wrong input), `MAX_REASON_LENGTH = 500`, `MAX_RAW_NOTES_LENGTH = 4_000` (independent of, though numerically equal to, `EVIDENCE_LIMITS.maxUntrustedTextLength` — one governs what a caller may submit, the other governs later truncation for a future model input; they're allowed to drift independently).
Alternatives: validate dates with a date-parsing library (rejected — a regex plus one `Date.UTC` round-trip check is sufficient and adds no dependency); allow `GENERAL_UPDATE` to accept supplier-delay fields "just in case" (rejected — the task explicitly calls for rejecting them unless deliberately supported and documented, which they are not).

## 2026-07-18 (Phase 3) — Mutation authorization: `FORBIDDEN` extends the Phase 2 error strategy; database role is always re-verified, never trusted from a session claim

Extended `DomainErrorCode` (`packages/core/src/analysis/types.ts`) from `"NOT_FOUND" | "VALIDATION_ERROR"` to add `"FORBIDDEN"`, with a matching `forbidden()` constructor — the same `ServiceResult<T>` shape every Phase 2 service already returns, not a second error strategy for mutations.

## 2026-07-20 (Phase 4) — Retry policy is uniform across AI modes, not gated on `AI_MODE`

`orchestrator.ts`'s attempt loop (max 2 attempts, retry exactly once on a retryable failure category) has no `if (aiMode === "live")` branch — it retries identically regardless of which provider produced the failure. Fixed by making these two imports dynamic (`await import(...)`) inside `seedImpactAnalysis()` itself, which only evaluates at the point it's actually awaited — by which time `main()`, and therefore the `dotenv` load, has already run. `seed.ts`'s pre-existing imports of `../src/seed/ids` and `../src/db-safety` were never affected by this, since neither transitively imports `../db.ts`.
New fixed seed IDs (`packages/core/src/seed/ids.ts`): `ANALYSIS_IDS`, `ANALYSIS_RUN_IDS`, `ANALYSIS_TRACE_IDS`, `MITIGATION_OPTION_IDS` (always exactly 3), `ANALYSIS_AUDIT_EVENT_IDS`. `SourceReference` row IDs are deliberately _not_ a pre-enumerated fixed list — they're derived deterministically at seed time from each cited record's own `(recordType, recordId)`, since the exact evidence-citation set is itself already fully deterministic seed data; pre-enumerating a parallel ID list whose length must exactly match the pipeline's real output would be fragile for no real benefit.
Alternatives: hand-author the seeded analysis's executive summary/mitigation options directly as static seed data (rejected — the task explicitly requires reusing the same validated mock-output fixture the pipeline itself produces, not a separate duplicate shape); run the seeded analysis through the full `runImpactAnalysis()` orchestrator instead of calling the lower-level functions directly (rejected — the orchestrator's authorization/attempt-lifecycle machinery has no meaning at seed time, when there's no authenticated actor session; calling `buildAnalysisEvidence`/`buildModelInputProjection`/`generateMockImpactAnalysis` directly is the minimal real subset that still proves the pipeline produces valid, schema-passing output).

## 2026-07-21 (Phase 4 correction pass) — `mitigationOptions` output field: `z.array(...).length(3)` instead of `z.tuple([...])`

Confirmed as a real, reproducible defect (not yet caught because the live provider had never actually been exercised): `impactAnalysisOutputSchema.mitigationOptions` was a `z.tuple([opt, opt, opt])`. `z.toJSONSchema()` converts a Zod tuple to JSON Schema's `prefixItems` (positional-item array validation) — a keyword outside OpenAI Structured Outputs' documented supported subset. A live request built with the original schema would very likely have been rejected by the API (or silently fallen back to non-strict enforcement), and this was never caught locally because no automated test may call the live provider (see the entry directly above) and the mock provider never exercises the JSON-schema-generation path at all.
Fix: `mitigationOptions: z.array(mitigationOptionOutputSchema).length(3, "exactly three mitigation options are required")`. `z.array(...).length(n)` converts to `{ type: "array", items: <schema>, minItems: n, maxItems: n }` — verified directly (`z.toJSONSchema()` output inspected before and after) — which expresses the identical "exactly three" constraint using only `items`/`minItems`/`maxItems`, all of which are in OpenAI's supported subset. Zod's own runtime validation is unweakened: `.length(3)` still rejects any array whose length isn't exactly 3 (verified: 2 elements and 4 elements both fail `safeParse`, exactly 3 passes), and the pre-existing `.refine()` requiring exactly one `isRecommended: true` is untouched.
Type consequence: `ImpactAnalysisOutput["mitigationOptions"]` is now `MitigationOptionOutput[]` rather than a compile-time 3-tuple. No caller relied on tuple-specific typing (all iterate with `.map()`/`.entries()`/`for...of`), so this had no other code impact.
Alternatives: keep the tuple and manually strip `prefixItems` from the generated JSON Schema before sending it (rejected — would mean the JSON Schema sent to the provider no longer accurately reflects an array of exactly 3 homogeneous items, replacing it with something that isn't equivalent JSON Schema for that constraint); switch to `z.tuple([...]).length ...` (not a real Zod API — tuples don't support `.length()`).

## 2026-07-21 (Phase 4 correction pass) — Provider-facing JSON Schema subset: generated from the authoritative schema, then verified, not hand-maintained

`packages/core/src/ai/openai-schema.ts` is new: `buildOpenAiImpactAnalysisJsonSchema()` generates a JSON Schema from `impactAnalysisOutputSchema` via `z.toJSONSchema()` (unchanged from the original Phase 4 approach — still the single authoritative source, never a second hand-maintained schema) and then recursively verifies the result with `assertOpenAiCompatibleJsonSchema()` before returning it. The verifier checks two things throughout the whole schema tree: (a) none of `prefixItems`, `unevaluatedItems`, `contains`, `minContains`, `maxContains`, `propertyNames`, `patternProperties` appear anywhere — keywords draft-2020-12 permits but OpenAI Structured Outputs strict mode does not document support for; (b) every object-typed schema node declares `additionalProperties: false` with every one of its `properties` listed in `required` (OpenAI strict mode has no concept of an optional property — this codebase already expresses optionality via `.nullable()`, never `.optional()`, specifically for this reason, unchanged from the original Phase 4 design).
Chose **verify, not silently normalize**: if `z.toJSONSchema()` ever produced a disallowed keyword in the future (e.g., a future field added via `z.record()` or `z.string().regex()` combined with a schema shape that emits `patternProperties`), this throws a clear, located error at module load time rather than silently stripping or rewriting the offending keyword — a schema this function had to "fix" would mean the JSON Schema actually sent to the provider no longer matches what `impactAnalysisOutputSchema` really requires, which is a correctness bug worth failing loudly on. `openai-provider.ts` now imports `buildOpenAiImpactAnalysisJsonSchema()` instead of calling `z.toJSONSchema()` inline.
Known residual risk, documented rather than guessed away: OpenAI's own documented "supported subset" isn't published as a machine-checkable spec, so this allowlist-of-disallowed-keywords was assembled from Structured Outputs documentation and cannot be verified against a real API response in this repository (see "Live AI mode is unverified..." above). If a real live run is ever performed and OpenAI rejects the schema for a reason not on this list, the fix is to extend `OPENAI_DISALLOWED_JSON_SCHEMA_KEYWORDS`, not to bypass the check.
Alternatives: validate the schema only informally via manual inspection before each release (rejected — the task requires this be directly testable, and a regression here would only be caught by an actual failed live call, which this project is expressly forbidden from making in automated contexts); maintain a fully separate, hand-written OpenAI-specific schema (rejected — reintroduces exactly the drift risk the original Phase 4 design (generate from the authoritative schema) was built to prevent).

## 2026-07-22 (Phase 4 persistence-boundary repair) — Provider failures separated from persistence failures; new non-retryable `PERSISTENCE_FAILURE` category

Confirmed as a real, reproducible defect: `persistSucceededAttempt()` previously executed inside the same broad `try/catch` that wrapped the provider invocation. An unexpected Prisma error during success persistence (connection drop, constraint violation, anything) was caught by that `catch` block and routed through `classifyProviderError()`, which has no way to distinguish "the provider failed" from "the database write failed" — it would default to `TRANSIENT_PROVIDER_FAILURE`, a retryable category. Since `TRANSIENT_PROVIDER_FAILURE` triggers a retry, this meant a provider response that was already valid and already accepted could cause a **second, unnecessary provider call** purely because the _write_ of the first, good response failed — wasted cost (and, in live mode, wasted spend) for a failure that had nothing to do with the provider.
Fix: the attempt loop is now five explicit stages — provider invocation, provider response parsing, structural validation, semantic validation, success persistence — and only the first of these (plus any provider-originated parsing error thrown from inside the provider call, e.g. `AiProviderError("...", "MALFORMED_JSON")`) is covered by a `try/catch` that calls `classifyProviderError()`. This is implemented as a new pure-ish helper, `runProviderAndValidate()`, whose own `try/catch` wraps only `await provider.generateImpactAnalysis(request)`; structural and semantic validation happen afterward, outside that `catch`, and never throw (`safeParse` / a validity-result object). `persistSucceededAttempt()` now runs in a separate `try/catch` entirely outside `runProviderAndValidate()`, in the orchestrator's own loop body.
Added `PERSISTENCE_FAILURE` to `AI_ERROR_CATEGORIES` (`errors.ts`) — deliberately **not** added to `RETRYABLE_CATEGORIES`. A broken persistence layer isn't fixed by asking the provider to try again, and retrying would call the provider a second time for a response it had already produced correctly. Every other category's retryability is unchanged: `TRANSIENT_PROVIDER_FAILURE`/`MALFORMED_JSON`/`INVALID_OUTPUT_SCHEMA`/`SEMANTIC_VALIDATION_FAILED` remain retryable; `CONFIGURATION_ERROR`/`PERSISTENCE_FAILURE` remain (or become) non-retryable.
Behavior on a success-persistence failure (`recordPersistenceFailureAfterValidOutput()`): the provider is never called again; `analysis.retrying` is never logged; the attempt is marked `FAILED`/`PERSISTENCE_FAILURE` through a **separate** call into the persistence interface (not a retry of the write that just failed, but not the same call either — a fresh, narrower update attempt); `ANALYSIS_FAILED` is only created if that FAILED-marking call itself succeeds; the already-committed complete evidence snapshot from `persistPendingAttempt()` is untouched (it lives in an earlier, already-committed transaction); zero `MitigationOption` rows survive, since `persistSucceededAttempt()`'s own transaction rolled back atomically. If even the FAILED-marking call fails, the function returns a generic, safe infrastructure-failure `ServiceResult` rather than claiming either "the provider failed" or "the failure was recorded" — neither of which would be true.
Behavior on a pending-attempt persistence failure (`persistPendingAttempt()` itself failing, before the provider is ever called): the provider is never invoked, no further attempt is started, and the function returns the same generic safe infrastructure-failure result immediately — `persistPendingAttempt()`'s own `prisma.$transaction(...)` guarantees that none of its three writes (the `PENDING` row, the evidence snapshot, the `ANALYSIS_STARTED` audit event) survive a failure partway through, so there is no risk of the caller mistaking a rolled-back attempt for a real one.
Every caught persistence error is discarded entirely — never read, logged, persisted, or included in a returned message. Verified directly with an injected error message resembling a leaked connection string (`"DATABASE_URL=postgresql://user:password@host/database"`): neither the returned `ServiceResult`, the persisted `ImpactAnalysis`/`SourceReference` rows, nor any structured log line emitted during the run contains any fragment of that string.
Alternatives: classify persistence errors more granularly (e.g., distinguish a constraint violation from a connection failure) (rejected as unnecessary scope for this pass — the task calls for one safe, non-retryable category, and finer-grained persistence-error taxonomy can be added later if a real operational need for it appears); retry persistence failures a bounded number of times before giving up (rejected — the task explicitly requires `PERSISTENCE_FAILURE` to be non-retryable, and a transient write failure retried automatically would reintroduce the exact "provider called again for no provider-side reason" problem this fix removes, just one layer down).

## 2026-07-22 (Phase 4 persistence-boundary repair) — Directly testable persistence injection: `AnalysisPersistence`, no global Prisma mocking

## 2026-07-22 (Phase 5) — One decision per mitigation option, enforced by a database constraint, not just application logic

`Decision.mitigationOptionId` gained `@unique` (replacing a plain, non-unique index), and `MitigationOption.decisions Decision[]` became `decision Decision?`. This is the primary correctness guarantee behind SPEC.md's approval state machine (`PENDING → APPROVED | REJECTED | REVISION_REQUESTED`, no transition out of a terminal state, no second decision on an already-decided option): `recordMitigationDecision()` (`packages/core/src/approvals/record-decision.ts`) checks `MitigationOption.status === "PENDING"` and "no existing `Decision`" before writing, but the `@unique` constraint is what actually prevents two concurrent calls from both succeeding — if both pass the pre-checks (a genuine race), only the first `tx.decision.create()` can commit; the second fails with a Postgres unique-constraint violation (`P2002` on `mitigationOptionId`), caught and reported as the new `CONFLICT` `DomainErrorCode` (see the next entry), never silently accepted as a second decision. `MitigationOption.status`'s own transition additionally uses a conditional `updateMany(... WHERE status = 'PENDING')` as defense in depth, though the Decision constraint is what actually closes the race.
Migration: `20260722000000_phase5_decision_state_machine`, generated via the established non-interactive shadow-database `migrate diff` technique (this environment has no interactive TTY for `prisma migrate dev`), applied to `missionthread_dev` and, later, `missionthread_test`. The same migration also made `ProposedChange.targetRecordId`/`targetRecordType` nullable (see the `NEW_ACTION` entry below) and made `Decision.rationale` required (`String?` → `String`, since a rationale is mandatory for every verdict — verified zero existing `Decision` rows before tightening the column, so no backfill was needed).

## 2026-07-22 (Phase 5) — New `CONFLICT` `DomainErrorCode`

`packages/core/src/analysis/types.ts`'s `DomainErrorCode` gained `"CONFLICT"` and a matching `conflict()` constructor, alongside the existing `NOT_FOUND` / `VALIDATION_ERROR` / `FORBIDDEN`. Distinct from `VALIDATION_ERROR` (malformed input) and `NOT_FOUND` (the record never existed): a `CONFLICT` means the input is well-formed and the record exists, but proceeding would either silently overwrite a decision that already happened (an already-decided mitigation option) or a domain change nobody actually approved (a stale proposed change — see below). Used by `recordMitigationDecision()` for a second decision attempt and by `applyApprovedChanges()` for both a stale proposed change and a genuine concurrent double-apply.

## 2026-07-22 (Phase 5) — Decision permissions revalidated from the database inside the transaction, mirroring the Phase 3/4 pattern

Program Manager may approve, reject, request revision, and apply; Engineering Lead may only request revision; Executive Viewer may never mutate. `recordMitigationDecision()` and `applyApprovedChanges()` both re-fetch the actor's current role from the database — never a session/JWT claim — using the identical pattern `recordProgramEvent()` (Phase 3) and `runImpactAnalysis()` (Phase 4) already established. `apps/web`'s decision/apply pages also gate which controls render (a Program Manager sees Approve/Reject/Request-revision; an Engineering Lead sees only Request-revision; an Executive Viewer sees no mutation controls at all), but this is a UX convenience only — exactly as documented for every earlier phase's mutation, hiding a button is never the actual security boundary. Verified with a role-change-between-calls test (identical in shape to Phase 3's): a temporary user starts as Engineering Lead (approval rejected as `FORBIDDEN`), is promoted to Program Manager, and the identical call then succeeds — proving the check reads current state, not a cached claim.

## 2026-07-22 (Phase 5) — Decision input contract: a strict Zod discriminated union keyed by `verdict`, never a client-supplied old value

`packages/core/src/approvals/schemas.ts`'s `recordDecisionInputSchema` is a `z.discriminatedUnion("verdict", [...])` with three `.strict()` branches. Only `APPROVED` has a `proposedChanges` field at all (required, `min(1)`) — `REJECTED`/`REVISION_REQUESTED` reject the key outright via `.strict()`, not merely ignore it. `rationale` is required on every branch (`RATIONALE_MIN_LENGTH = 10`, `RATIONALE_MAX_LENGTH = 2000`, the same "documented, deliberately generous-but-bounded limit" discipline as `packages/core/src/events/schemas.ts`'s `MAX_REASON_LENGTH`). `actorUserId`, role, analysis ID, program ID, status, trace ID, and every server-generated snapshot value are never fields of this schema at all — there is nowhere in its shape for a caller to put them, which is a stronger guarantee than "validated and rejected if present."
Each proposed change is itself a `z.discriminatedUnion("changeType", [...])` of four `.strict()` branches (`MILESTONE_DATE`, `RISK_UPDATE`, `BUDGET_UPDATE`, `NEW_ACTION`) — see the `NEW_ACTION` entry below for why the shapes differ on `targetRecordId`/`targetRecordType`. None of the four branches accepts `oldValue`; the client may only submit the _proposed_ new value (or, for `RISK_UPDATE`/`BUDGET_UPDATE`, a subset of writable fields) — see the server-generated-snapshot entry below for how `oldValue` is actually produced.

## 2026-07-22 (Phase 5) — Resolved: `ProposedChangeType.NEW_ACTION` target-field conflict (deferred in a 2026-07-18 second-correction-pass entry)

`ProposedChange.targetRecordId`/`targetRecordType` are now nullable (`String?`/`RecordType?`) — `NEW_ACTION` has no existing record to target, unlike the other three change types, and the client-submitted schema for it (`newActionProposedChangeInputSchema`) requires both fields present as literal `null` (not omitted), so every proposed-change input shape explicitly states its target rather than three variants having the field and one silently lacking it. Enforced entirely at the Zod layer (`packages/core/src/approvals/schemas.ts`) and by `buildProposedChangeSnapshot()` (`packages/core/src/approvals/snapshot.ts`), never by a database constraint — Prisma has no conditional-nullability rule tying a `changeType` enum value to whether its target fields must be null or non-null.
`NEW_ACTION`'s safe canonical `oldValue` is always `{}` (there is nothing to have had a prior value), and its `newValue` is the bounded structured payload `{ title, description, dueDate }` (`NEW_ACTION_TITLE_MAX_LENGTH = 200`, `NEW_ACTION_DESCRIPTION_MAX_LENGTH = 2000`, `dueDate` a nullable `YYYY-MM-DD` string). No separate `ActionItem` model was introduced — for this MVP, the applied `ProposedChange` row itself is the durable action record; see the next entry for how it's surfaced.

## 2026-07-22 (Phase 5) — `NEW_ACTION` has no domain table of its own; the program-overview "Actions" section reads applied `ProposedChange` rows directly

Because `NEW_ACTION` was deliberately not given a separate `ActionItem` model (previous entry), applying one (`applyApprovedChanges()`) performs no domain mutation for it at all — the mutation loop's `NEW_ACTION` branch is a no-op, and the row is simply marked `APPLIED` like every other proposed change. `apps/web/src/app/(app)/programs/edgelink-x/page.tsx` gained an "Actions" section that queries `ProposedChange` directly (`changeType: "NEW_ACTION"`, `status: "APPLIED"`, joined through `mitigationOption.impactAnalysis.programEvent.programId` to scope it to `PROGRAM-EDGELINK-X`) and renders each row's `newValue` (`title`/`description`/`dueDate`) plus its `appliedAt` timestamp. If this MVP representation ever proves insufficient (e.g. an action needing its own status/assignee lifecycle independent of the proposed-change record that created it), a real `ActionItem` model can be introduced later — not needed yet.

## 2026-07-22 (Phase 5) — Server-generated proposed-change snapshots: the client proposes a new value, the server builds both old and new

`buildProposedChangeSnapshot()` (`packages/core/src/approvals/snapshot.ts`) is the single place every proposed change's persisted `oldValue`/`newValue` pair is constructed, called identically from `recordMitigationDecision()` (decision time) and reused, via the read-only `checkProposedChangeStale()` comparison (`stale.ts`), at both apply-preview render time and inside `applyApprovedChanges()`'s own transaction. For `MILESTONE_DATE`/`RISK_UPDATE`/`BUDGET_UPDATE`, it: loads the target record, verifies it belongs to `PROGRAM-EDGELINK-X` (a nonexistent ID and an ID from another program produce the identical `NOT_FOUND`, matching `recordProgramEvent()`'s established non-distinguishing pattern), and builds `oldValue` from the record's _current_ database row — never from anything the client sent. `oldValue` and `newValue` intentionally share the same key set (e.g. a `RISK_UPDATE` proposing only `status` produces `oldValue: { status: "OPEN" }`, `newValue: { status: "MITIGATING" }`, with no `severity`/`probability`/`impact` keys at all), so the generic stale-comparison helper can walk `Object.keys(oldValue)` without a second changeType switch. Every value uses the same normalized representation used elsewhere in this codebase: UTC date-only strings (`toISOString().slice(0, 10)`, matching `schedule.ts`/`traceability.ts`'s established helper), fixed-two-decimal monetary strings (`Prisma.Decimal.toFixed(2)`, matching `budget.ts`), and Prisma enum strings verbatim.

## 2026-07-22 (Phase 5) — Stale-data conflict detection: normalized comparison, shared between preview and apply, never a silent overwrite

`checkProposedChangeStale()` (`packages/core/src/approvals/stale.ts`) reloads only the fields a stored proposed change's captured `oldValue` actually contains and compares them against the record's current value, using the identical normalization `buildProposedChangeSnapshot()` used when the value was first captured — so a value that hasn't really changed can never register as stale from a representation mismatch alone. A target record that no longer exists (or no longer belongs to the program) is treated as "every captured field changed," never as "nothing to compare." The apply-preview route (`.../options/[optionId]/apply/page.tsx`) calls this at render time, read-only, against the live `prisma` client directly (not inside a transaction — nothing is mutated while rendering); `applyApprovedChanges()` calls the identical function again inside its own transaction immediately before applying, since time can pass between viewing a preview and clicking apply. A stale proposed change blocks the _entire_ apply batch, not just itself — see the all-or-nothing entry below.

## 2026-07-22 (Phase 5) — Decision transaction: one `Decision`, the option's status transition, proposed changes (approval only), and one `DECISION_RECORDED` audit event, atomically

`recordMitigationDecision()` runs its full step sequence — actor revalidation, permission check, option/program lookup, PENDING/no-existing-decision checks, proposed-change validation and server-side snapshot construction, `Decision` creation, status transition, `ProposedChange` creation (approval only), and the audit event — inside one `prisma.$transaction(...)` callback, mirroring the transaction-boundary discipline established in `recordProgramEvent()` and `runImpactAnalysis()`. A forced failure partway through (e.g. one proposed change targets a nonexistent record) rolls back everything already attempted in that call — verified directly with a two-proposed-change approval where the second change's target doesn't exist: zero `Decision` rows, the option still `PENDING`, zero `ProposedChange` rows.
The `DECISION_RECORDED` audit event's `afterValue` is a bounded, safe structured payload — verdict, mitigation-option ID, analysis ID, proposed-change IDs and their change types, and a `hasRationale` boolean — and deliberately never the rationale text itself, which stays only on the `Decision` row. Verified directly: a rationale containing a marker string never appears anywhere in the persisted `AuditEvent.afterValue` JSON, while the same marker is confirmed present on the `Decision` row.

## 2026-07-22 (Phase 5) — Apply transaction: exact `"APPLY"` confirmation, stale check inside the transaction, all-or-nothing domain mutation, one shared `appliedAt`

`applyApprovedChanges(mitigationOptionId, actorUserId, confirmation)` (`packages/core/src/approvals/apply-changes.ts`) requires `confirmation` to equal the exact literal `APPLY_CONFIRMATION_VALUE = "APPLY"` — read directly from a real form field the apply-preview page renders, never a hidden Boolean the server would otherwise have no way to distinguish from an unattended default. Actor and role (`PROGRAM_MANAGER` only) are revalidated from the database _before_ any transaction opens, so an unauthorized caller never causes a transaction to be opened at all. Inside the transaction: reload the option (require `APPROVED`), load the unique `APPROVED` decision, load every `PENDING` proposed change (require at least one — see the idempotency entry below for why this is also how a repeated apply is rejected), reload and compare every target against its captured `oldValue` via `checkProposedChangeStale()`, and — only if _none_ are stale — apply each domain mutation (allowlisted fields only: a milestone's `currentDate`, a risk's proposed subset of `status`/`severity`/`probability`/`impact`, a budget item's proposed subset of `plannedAmount`/`actualAmount`; `NEW_ACTION` mutates no domain table at all). One `appliedAt` timestamp, computed once before the transaction opens, is used for every `ProposedChange` row the transaction marks `APPLIED` in a single `updateMany`, so every change from one apply call shares the identical value (verified directly: two proposed changes in one approval, one `Set` of their `appliedAt.getTime()` values has size 1).
All-or-nothing: a single stale proposed change aborts the entire batch before any domain mutation runs (the stale check loop completes fully before the mutation loop begins) — verified with a two-change approval where only one target was made stale after approval: the fresh change's target record is unchanged, and both `ProposedChange` rows remain `PENDING`. No AI or network request runs inside this transaction — there is no code path in `applyApprovedChanges()` that could reach one.

## 2026-07-22 (Phase 5) — Idempotency and concurrency: database constraints and conditional claims, never a process-local flag

A repeated apply request naturally fails, not merely "is prevented": once every `ProposedChange` for an option is `APPLIED`, a second call finds zero `PENDING` rows and returns `VALIDATION_ERROR` ("no pending proposed changes to apply") before touching anything else — no duplicate audit event, no altered `appliedAt`, no duplicate `NEW_ACTION` record, because there is nothing left for the transaction to act on. Genuine concurrency (two apply calls racing on the same still-`PENDING` set) is closed by the transaction's final step: a conditional `proposedChange.updateMany(... WHERE status = 'PENDING')` that claims the exact set of rows about to be marked `APPLIED`; if the returned count doesn't match the expected count (the other transaction claimed some or all of them first), the whole transaction throws and rolls back, including any domain mutations already applied inside it — caught and reported as `CONFLICT`. Verified directly: two concurrent `applyApprovedChanges()` calls against the same freshly-approved option produce exactly one successful apply and exactly one `CHANGES_APPLIED` audit event, never two, never zero. The same discipline (a DB-constraint-backed conditional claim, not an in-memory lock) is what makes `recordMitigationDecision()`'s concurrent-decision guarantee real — see the one-decision-per-option entry above; nothing in this phase relies on a process-local flag or lock, which would not even be correct across the multiple server processes/serverless invocations this application's own architecture already assumes elsewhere (see `packages/core/src/db.ts`'s singleton-per-process comment).

## 2026-07-22 (Phase 5) — `CHANGES_APPLIED` audit payload: bounded before/after values, applying user, apply trace ID, linked to the decision

The `CHANGES_APPLIED` `AuditEvent` (`decisionId` set, linking it back to the `Decision` that authorized it) carries a structured `afterValue`: the mitigation-option and decision IDs, every applied proposed-change ID/type/target-record-ID/target-record-type, the same already-safe `beforeValues`/`afterValues` arrays already persisted on each `ProposedChange` row (never raw provider output or untrusted supplier text — those never entered this pipeline in the first place, since proposed-change values only ever come from allowlisted domain fields or the bounded `NEW_ACTION` payload), the applying user's ID, and the shared `appliedAt` timestamp. One apply trace ID (the `AuditEvent.traceId`) covers the whole batch, the same "one trace ID per logical operation" convention `DECISION_RECORDED`/`ANALYSIS_STARTED`/`EVENT_RECORDED` already use.

## 2026-07-22 (Phase 5) — Test suite: disabled cross-file parallelism after a genuine race between new and existing tests

Confirmed as a real, reproducible flake, not a one-off: Vitest runs test files in parallel worker processes by default, and this phase's new integration tests (`apply-changes.test.ts`) legitimately need to mutate real domain rows (a milestone's `currentDate`, a risk's fields) to prove `applyApprovedChanges()` actually changes them — but several pre-existing test files (`readiness-snapshot.test.ts`'s historical-immutability check, `evidence.test.ts`'s exact-seeded-value assertions) compute whole-program aggregates or exact-match assertions over the _same_ seeded `PROGRAM-EDGELINK-X` data, expecting it to stay stable for their entire test's duration. Running both kinds of test in parallel let them transiently race — reproduced directly (a different, non-deterministic test failed on each of several consecutive full-suite runs before the fix, and none after).
Fix, in two parts: (1) `apply-changes.test.ts` was rewritten to create its own uniquely-IDed temporary `Component`/`Milestone`/`Risk`/`BudgetItem` fixtures (cleaned up in `afterEach`/`afterAll`) rather than mutating the shared seeded `MS-001`/`RISK-001`/`BUDGET-001`/`COMP-EC440` rows at all — the same "temp, uniquely-IDed, always cleaned up" convention every other DB-backed test in this repo already follows for negative-path fixtures (e.g. `record-program-event.test.ts`'s "other program" tests). Alternatives: keep parallel execution and rely solely on unique temp fixtures everywhere (rejected as insufficient defense in depth — a future test author could easily reintroduce a shared-row mutation without realizing the race risk, since nothing would signal it locally); use Vitest's `sequence.shuffle`/isolated worker-per-file database schemas (rejected — far more complex than this project's test-suite size or CI budget justifies).

## 2026-07-23 (Phase 5 correction) — Reject overlapping proposed-change writes within one approval

Confirmed as a real, reproducible defect: `proposedChangeInputSchema` validated each proposed change independently, but never checked whether two changes in the same approval batch would write the same field on the same record (e.g. two `MILESTONE_DATE` entries for `MS-001`, or two `RISK_UPDATE` entries both proposing a new `status` for `RISK-001`). Every entry in such a batch independently passes its own stale check (each compares against the _current_ database value, which hasn't changed yet when the batch starts applying), so `applyApprovedChanges()`'s domain-mutation loop would apply both writes to the same field in array order — the final persisted value would depend on which proposed change happened to be listed last, not on anything a human reviewer could see or control from the apply-preview page (which shows every proposed change, but not that two of them silently overwrite each other).
Fix: `packages/core/src/approvals/overlap.ts`. `getProposedChangeWriteKeys(change)` derives one write key per field a proposed change actually supplies — `<targetType>:<targetId>:<field>`, e.g. `"RISK:RISK-001:status"` — from the client-submitted `ProposedChangeInput` shape; `NEW_ACTION` always returns zero keys, since it creates a new, independent record every time rather than overwriting an existing field, so multiple `NEW_ACTION` entries (even with identical titles) never conflict with each other or with anything else. `validateNoOverlappingProposedChanges(changes)` finds the first write key that appears more than once across the batch and returns `VALIDATION_ERROR` naming the conflicting target and field — `recordMitigationDecision()` calls it immediately after Zod parsing and before any database access at all (before the transaction opens, before any target is loaded, before the `Decision` row is created), so an overlapping batch never opens a transaction or creates any row. The error message is built entirely from the write key's own components (an already-validated, allowlisted field name and a program-scoped entity ID), never from arbitrary client-submitted free text.
Verified: two `MILESTONE_DATE` entries for the same milestone, two `RISK_UPDATE` entries writing the same field, two `BUDGET_UPDATE` entries writing the same field, and two byte-identical proposed changes are all rejected with zero `Decision`/`ProposedChange`/`AuditEvent` rows created and the option left `PENDING`; disjoint fields on the same risk/budget item, updates to different targets, and multiple `NEW_ACTION` entries all remain valid in one batch.
Alternatives: detect the conflict only at apply time, after decision creation (rejected — a decision that can never actually be applied without a follow-up correction is a worse failure mode than refusing it at the point a human is still reviewing what they're approving); silently keep only the last write per field (rejected — this would silently discard a proposed change a human reviewer believed had been approved, exactly the "silent overwrite" failure this whole phase's stale-data protection exists to prevent elsewhere).

## 2026-07-23 (Phase 5 correction) — Apply-time revalidation of persisted `ProposedChange` rows against strict, changeType-keyed schemas

Confirmed as a real gap, not yet exploited but present: `applyApprovedChanges()`'s domain-mutation code (`applyDomainMutation()`) read a stored `ProposedChange` row's `oldValue`/`newValue` as `unknown`, then used non-null assertions (`change.targetRecordId!`) and blind casts (`newValue as Record<string, unknown>`, `data as Prisma.RiskUpdateInput`) to treat it as trustworthy — a TypeScript assertion, not a runtime check. Decision-time validation (`recordDecisionInputSchema`, `buildProposedChangeSnapshot()`) is the normal boundary for what gets written in the first place, but nothing re-verified that boundary still held by the time a row was read back for the irreversible apply step — a future migration gap, a direct database edit, or a bug in an earlier version of this code could have produced a malformed or internally inconsistent stored row, and the apply transaction would have trusted it anyway.
Fix: `packages/core/src/approvals/persisted-schemas.ts` defines strict, `changeType`-keyed schemas for exactly what a persisted row must contain — `MILESTONE_DATE` requires a non-null `targetRecordId`, `targetRecordType: "MILESTONE"`, and `oldValue`/`newValue` each exactly `{ currentDate: <valid YYYY-MM-DD> }`; `RISK_UPDATE`/`BUDGET_UPDATE` require a non-null target, the matching `targetRecordType`, and `oldValue`/`newValue` carrying the identical non-empty key set restricted to their allowlisted writable fields (`status`/`severity`/`probability`/`impact`, or `plannedAmount`/`actualAmount`, each validated against the same schemas/ranges the input contract already uses); `NEW_ACTION` requires `targetRecordId`/`targetRecordType` both `null`, `oldValue` exactly `{}`, and a strict `{ title, description, dueDate }` `newValue`. `parsePersistedProposedChange(row)` parses one row against the schema its `changeType` selects and never throws — every failure becomes a safe `{ ok: false, message }` result, never a raw Zod error or the row's own JSON content.
`applyApprovedChanges()` now parses every `PENDING` row this way immediately after loading them (before any stale check or domain mutation); any parse failure returns `VALIDATION_ERROR` naming the offending row's ID and aborts before anything else happens. The parsed, typed result also revalidates for a stored _cross-row_ overlap (`getPersistedProposedChangeWriteKeys()` + `validateNoOverlappingPersistedProposedChanges()` — the persisted-row equivalent of the decision-time check above, in case a stored batch was ever assembled or edited outside the normal path). `applyDomainMutation()` was rewritten to take the now-fully-validated shape directly: `change.targetRecordId` is a real `string` (not `string | null`) for every branch that uses it, and `change.newValue` is a typed, allowlisted-field object — every non-null assertion and blind cast in this function is gone, replaced by an actual runtime guarantee.
Verified: a row with the wrong `targetRecordType`, a malformed `oldValue`, a malformed `newValue`, a mismatched `oldValue`/`newValue` key set, and a directly-inserted stored-batch overlap (two individually-valid rows whose fields were made to collide after decision creation) are all rejected before any domain mutation, with the underlying target record proven unchanged afterward in every case; a batch with one malformed row alongside one well-formed row applies neither.
Alternatives: trust the decision-time validation permanently and skip apply-time revalidation (rejected — this is exactly the "TypeScript cast as a substitute for a runtime check" pattern the task calls out, and the irreversible apply step is the wrong place to discover that assumption was wrong); validate only `targetRecordType`/non-null-ness and skip the full shape check (rejected — a narrower check would still trust an unvalidated `oldValue`/`newValue` shape into `Prisma.RiskUpdateInput`/`Prisma.BudgetItemUpdateInput`, which is exactly where the original non-null-assertion risk lived).

## 2026-07-23 (Phase 5 correction) — Playwright test restores its own bounded changes in a `try`/`finally`, never a full reset

## 2026-07-24 (Phase 5 correction) — Playwright database-isolation repair: one authoritative test environment, never derived independently by the web server and the worker

Confirmed as a real, reproducible defect: `playwright.config.ts` loaded `.env.test` via `loadEnv({ path: ... })` with no `override: true`. Dotenv's default behavior never overwrites a key already present in `process.env` — so an ambient `DATABASE_URL` already set in the invoking shell (e.g. a developer's own local session, still pointed at `missionthread_dev` for ordinary work) survived untouched. The `webServer.env` config explicitly spread `testEnv.parsed` (the `.env.test` file's own parsed content, independent of the `override` option) into the spawned `next start` child process, so the **browser-driven Next.js server always correctly used `missionthread_test`** — but `e2e/decision-workflow.spec.ts` statically imported `{ prisma } from "@missionthread/core"` at module load time, and `packages/core/src/db.ts`'s `createPrismaClient()` reads `process.env.DATABASE_URL` directly — the Playwright **worker process's own, still-ambient value**, never the `.env.test` value the web server received. A developer running `npm run test:e2e` from a shell already configured for local dev work could therefore have the test's own cleanup queries (and its `milestoneBefore` read) silently execute against `missionthread_dev` while the browser it drove correctly talked to `missionthread_test`.
Fix, fail-closed throughout:

- **One pure resolver.** `apps/web/e2e/playwright-test-environment.ts`'s `resolvePlaywrightTestEnvironment(ambientEnv, parsedTestEnv)` is the single place that decides what this suite's `DATABASE_URL` is. It requires `.env.test` to have loaded (a defined `parsedTestEnv`) and to define `DATABASE_URL`, parses and sanitizes it (never trusting the raw string), and accepts only `localhost:55432/missionthread_test`, `127.0.0.1:55432/missionthread_test`, or — solely when `ambientEnv.GITHUB_ACTIONS === "true"` — the GitHub Actions service-container tuple (`localhost:5432/missionthread_test`). `missionthread_dev`, the wrong port, a remote host, a malformed URL, and the GitHub Actions tuple outside a real GitHub Actions context are all rejected. It reuses `findApprovedDatabaseTarget()`, `sanitizeDatabaseUrl()`, `LOCAL_TEST_TARGETS`, and `GITHUB_ACTIONS_TEST_TARGETS` directly from `packages/core/src/db-safety.ts` — the exact same tuples and matching logic every other destructive-operation guard in this repo already uses — rather than a second, independently maintained allowlist.
- **Reused, not duplicated, via a new package subpath.** `packages/core/package.json` gained an `"exports"` map (`"." : "./src/index.ts"`, `"./db-safety": "./src/db-safety.ts"`), so `apps/web/e2e/playwright-test-environment.ts` can `import { ... } from "@missionthread/core/db-safety"` without importing the package's root barrel — which re-exports `db.ts`'s `prisma`, itself constructed eagerly at import time. `db-safety.ts` has no imports of its own and performs no side effects, so this subpath is genuinely inert to import. Verified the root `"@missionthread/core"` specifier (used everywhere else in `apps/web`) still resolves correctly after adding `"exports"` — a full production build and the complete test suite both pass unchanged.
- **Explicit replacement, one shared resolved environment.** `playwright.config.ts` now loads `.env.test` with `override: true`, fails immediately (throws before `defineConfig` is even reached) if `loadResult.error` is set or if `resolvePlaywrightTestEnvironment()` rejects the target, and then `Object.assign(process.env, resolvedTestEnvironment.env)` — applying the identical resolved values to both this config-loading process (and therefore every worker Node forks from it, since `child_process.fork()` inherits the parent's `process.env` at fork time) and `webServer.env`. Neither path derives its `DATABASE_URL` independently anymore.
- **Prisma is never imported before the target is proven.** The static `import { prisma } from "@missionthread/core"` was removed from `decision-workflow.spec.ts` entirely. `getPlaywrightTestPrisma()` calls `assertPlaywrightTestDatabaseTarget(process.env)` — the same rejection rules as the resolver above, re-checked independently rather than trusting that `playwright.config.ts`'s earlier assignment definitely propagated — and only then loads `@missionthread/core`, the point at which Prisma actually gets constructed. It then runs `SELECT current_database()` and confirms the live connection reports exactly `"missionthread_test"` — the URL-tuple check alone can't verify a connection pool or DNS layer didn't resolve somewhere else, and the database name alone can't verify host/port, so both checks stay mandatory together. The test calls `getPlaywrightTestPrisma()` once, before capturing `milestoneBefore` and before the `try`/`finally` even begins — if it throws, neither the main test body nor its cleanup `finally` block ever runs a single query, so a wrong database target produces zero mutations, never a fallback reset.
- **`require()`, not `await import()`, for that deferred load — a second real bug found and fixed along the way.** An `await import("@missionthread/core")` inside `getPlaywrightTestPrisma()` reproducibly failed with `SyntaxError: The requested module './db-safety' does not provide an export named 'GITHUB_ACTIONS_TEST_TARGETS'` — a genuine ESM dynamic `import()`, executed from inside a file Playwright compiles to CommonJS and loads via its own `require` transform hook, goes through Node's own native module loader for a second, independent load of the same package graph rather than staying on the loader that already successfully resolved `@missionthread/core/db-safety` earlier in the same file. Fixed by using `require("@missionthread/core")` instead (with an `eslint-disable-next-line @typescript-eslint/no-require-imports` justified inline, since this is deliberate, not an oversight) — staying on the single loader Playwright already uses consistently for every other import in this file removes the inconsistency entirely. Reproduced directly (the dynamic-`import()` version failed on every run; the `require()` version passed immediately and repeatedly) before committing to this as the fix rather than a coincidental workaround.
- **Every error message stays safe.** `sanitizeDatabaseUrl()` (reused, not reimplemented) already returns only host/port/database; every rejection message in `playwright-test-environment.ts` is built exclusively from that struct, never the raw connection string.
  Verified: 19 new pure unit tests (`e2e/playwright-test-environment.test.ts`) cover every acceptance/rejection case named above, including the exact regression this defect describes (ambient `DATABASE_URL` → `missionthread_dev`, `.env.test`'s own `DATABASE_URL` → `missionthread_test`, resolved worker environment → `missionthread_test`) and that no error message ever contains a username, password, query parameter, or the raw URL. `npm run test:e2e` run twice in a row after one authorized `npm run db:reset:test` both pass with no hidden reset (unchanged from the prior correction pass); a third run with an ambient `DATABASE_URL` deliberately pointed at `missionthread_dev` (while `.env.test` still correctly names `missionthread_test`) also passes, using only `missionthread_test` throughout — the regression scenario this whole repair exists to close.
  Alternatives: have the spec file read `.env.test` itself, independent of `playwright.config.ts` (rejected — this is exactly the "two independent paths can disagree" shape of the original defect, just relocated; one resolved environment, applied once, is the actual fix); trust `webServer.env` alone and assume the worker inherits the same values (rejected — this was the mistaken assumption behind the original bug; the worker and the `webServer` child process are different processes with different environment-inheritance rules, and nothing enforces that they'd agree without this fix); skip the `SELECT current_database()` check as redundant with the URL-tuple check (rejected — the task calls it optional but valuable, and it catches a class of failure (an actual connection landing somewhere the URL string didn't predict) the string-only check structurally cannot).

## 2026-07-24 (Phase 6) — In-memory analysis rate limiter: fixed window, 3 requests / 60 seconds, per authenticated actor

Why: `docs/SPEC.md` §12 requires a denial-of-wallet/denial-of-service control on the one operation in this system that spends real money in live mode (an impact analysis) and explicitly accepts an in-memory limiter for MVP as long as its process-local limitation is documented.
Decision: `packages/core/src/security/analysis-rate-limiter.ts`'s `AnalysisRateLimiter` — a fixed-window counter (`Map<actorId, { windowStartMs, count }>`), an injectable clock (`() => number`, defaulting to `Date.now`), `ANALYSIS_RATE_LIMIT_MAX_REQUESTS = 3` and `ANALYSIS_RATE_LIMIT_WINDOW_SECONDS = 60` as named, documented constants, lazy pruning of expired keys on every `checkAndConsume()` call plus a directly callable `pruneExpired()`, and a test-only `reset()` (production code never calls it). Identity is the authenticated actor's user ID — never a client IP, which is trivially spoofable/shared and would conflate or split real users incorrectly. `defaultAnalysisRateLimiter` is the one shared, process-wide instance the production web path always uses; `runImpactAnalysis(..., { rateLimiter })` accepts an isolated instance for tests/evals, mirroring the existing `options.provider`/`options.persistence` override-point shape.
A real bug was found and fixed while writing this module's own tests: the original `checkAndConsume()` unconditionally allowed the very first request for a brand-new key regardless of `maxRequests`, so a limiter configured with `maxRequests: 0` (used by a test deliberately forcing immediate denial) incorrectly allowed one request through. Fixed by computing `currentCount` for a fresh window as `0` and checking `currentCount >= this.maxRequests` before ever incrementing, rather than special-casing "no existing entry yet" as an automatic pass. Reproduced (the `maxRequests: 0` test failed) before the fix and passed after.
Alternatives: a token-bucket algorithm (rejected — a fixed window is simpler to reason about and test deterministically for this MVP's needs, and the spec explicitly allows either); a database-backed limiter (rejected — `docs/SPEC.md` and the Phase 6 authorization both explicitly forbid this, and it would add a database round-trip to the hot path of every analysis request for a feature whose whole job is to run _before_ any database write); client-IP-keyed limiting (rejected — see above).

## 2026-07-24 (Phase 6) — Rate-limiter integration point in `runImpactAnalysis()`

Decision: the limiter check runs immediately after event-existence validation and immediately before `buildAnalysisEvidence()` — i.e., after actor-ID validation, fresh database-role authorization, event-ID validation, and event-existence validation, but before any evidence/model-input construction, attempt persistence, or provider invocation. Consequences of this exact placement: an unauthorized caller (wrong role) is rejected by the authorization checks above and never reaches the limiter at all, so it can never consume another user's allowance; a malformed or nonexistent event is rejected before the limiter, so it never consumes quota; the limiter is checked exactly once per top-level `runImpactAnalysis()` call, not once per attempt inside the retry loop, so a provider retry inside one authorized run never consumes a second slot; a denied request returns before any `ImpactAnalysis`/`SourceReference`/`MitigationOption` row is created and before the provider is ever invoked.
A denied request logs a new `analysis.rate_limited` structured event (`ANALYSIS_LOG_EVENTS` in `logging.ts`) containing only the authenticated actor ID, event ID, retry-after seconds, AI mode, and a freshly generated trace ID for correlation — never the limiter's internal map state, another actor's activity, secrets, or untrusted text. Since a rate-limited request has no `analysisRunId`/`analysisId`/`attempt` (none were ever created), `AnalysisLogFields`' three corresponding fields became optional rather than inventing placeholder values for them.
New `RATE_LIMITED` added to `DomainErrorCode` (`packages/core/src/analysis/types.ts`), with a new `rateLimited(retryAfterSeconds, message)` constructor mirroring the existing `conflict()`/`forbidden()` pattern and an optional `retryAfterSeconds` field on `DomainError`. `apps/web`'s `analyzeEventAction()` needed no code change — it already redirects with `result.error.message` for any `!result.ok` outcome, and `rateLimited()`'s message is already safe to display verbatim (it never includes internal state).
Verified: existing `orchestrator.test.ts` (548 tests predating this limiter) needed a `beforeEach(() => defaultAnalysisRateLimiter.reset())` added, since many of its tests call `runImpactAnalysis()` repeatedly against the same seeded Program Manager actor without injecting an isolated limiter — none of those tests are about rate limiting, so resetting the shared default between them keeps the new cross-cutting control from incidentally interfering with unrelated assertions. This is the one existing test file that needed a setup-hook addition; no existing test body was rewritten. A dedicated `orchestrator-rate-limit.test.ts` (DB-backed, using the real orchestrator against the seeded event) and a pure `analysis-rate-limiter.test.ts` (no database) cover the full §7 list: first-N-pass/N+1-denied, window reset, independent actors (including two distinct real Program Manager users under one shared limiter), provider retries inside one call consuming exactly one slot, unauthorized/malformed-event-ID/nonexistent-event never consuming a slot, a denied request creating zero rows and calling the provider zero times, safe retry-after info in the returned error, no secrets/untrusted text in the `analysis.rate_limited` log line (verified directly against the seeded event's own deliberate prompt-injection rawNotes), and pruning.

## 2026-07-24 (Phase 6 correction pass) — Provider-spend and output-bounds

Four confirmed defects, fixed together as one security-boundary correction (each compounds the others): the OpenAI SDK's own automatic retries/timeout were left enabled, undermining the orchestrator's own retry cap; the live request had no output-token ceiling; several output strings had no maximum length; semantic-validation errors echoed untrusted provider-controlled values.

**1. The orchestrator is now the sole retry authority.** The official `openai` npm package enables 2 automatic retries and a 10-minute default timeout by default — both left active meant one orchestrator "attempt" (`packages/core/src/ai/orchestrator.ts`, `MAX_ATTEMPTS = 2`) could silently become up to 3 real HTTP requests, and a single request could hang for up to 10 minutes despite the orchestrator's own bound implying much less. Fixed via a new `buildOpenAiClientOptions(apiKey)` (`packages/core/src/ai/openai-provider.ts`) — a pure, directly-testable function returning `{ apiKey, maxRetries: OPENAI_SDK_MAX_RETRIES /* 0 */, timeout: OPENAI_REQUEST_TIMEOUT_MS /* 60_000 */ }` — used at the one place a real `OpenAI` client is constructed (`this.client = options.client ?? new OpenAI(buildOpenAiClientOptions(options.apiKey))`). A timeout still classifies through the existing transient-provider-failure path (`APIConnectionTimeoutError` in `toProviderError()`, unchanged) and is retried exactly like any other transient failure — the orchestrator's second attempt is the only retry that ever follows. Verified without a real network call: constructing a real `OpenAI` client from `buildOpenAiClientOptions("sk-test")` never itself opens a connection (the SDK connects lazily per-request, same as the already-established Prisma-construction precedent), so tests read the constructed client's own public `maxRetries`/`timeout` fields directly and assert `0`/`60_000` — plus a companion test constructing a client with no explicit options at all, confirming the SDK's real, unmodified defaults are `2`/>`60_000`, proving the override is load-bearing rather than redundant with an already-safe default.
Alternatives: pass `maxRetries`/`timeout` as per-request `RequestOptions` on each `responses.create()` call instead of at client construction (rejected — client-level configuration is simpler, applies uniformly with no risk of a call site forgetting to pass it, and is exactly as testable via the pure options-builder function); leave the SDK defaults and instead have the orchestrator detect/cancel an SDK-internal retry (rejected — the SDK exposes no hook for this; disabling it outright is the only reliable mechanism).

**2. `IMPACT_ANALYSIS_MAX_OUTPUT_TOKENS = 8192`, server-controlled, sent on every live request.** Added to the `responses.create()` call as `max_output_tokens`. Never derived from form data, a client request, or model output. Applies identically to production analyses and `npm run eval:live`, since both go through `OpenAiImpactAnalysisProvider`. A response whose `status === "incomplete"` and `incomplete_details?.reason === "max_output_tokens"` is never treated as successful (`response.output_text` in that state is a cut-off fragment, not necessarily even syntactically valid JSON) — thrown as a new `AiProviderError(..., "INCOMPLETE_OUTPUT")` _outside_ the try/catch that wraps the `responses.create()` call itself (so `toProviderError()` never reclassifies it), before the JSON-parse step ever runs, and never includes `response.output_text` in the thrown message. `INCOMPLETE_OUTPUT` added to `AI_ERROR_CATEGORIES` (`packages/core/src/ai/errors.ts`) as retryable — a shorter response on retry may fit within the same ceiling. An `incomplete` response for a _different_ reason (`content_filter`) is deliberately not caught by this specific check and falls through to normal JSON parsing, verified by a dedicated test.

**3. Complete per-string output bounds.** `OUTPUT_LIMITS` (`packages/core/src/ai/output-schema.ts`) gained `maxRecordIdLength: 128`, `maxVerificationCategoryLength: 64`, `maxAssumptionLength: 500`, `maxUnknownLength: 500`. One shared `outputRecordIdSchema = z.string().min(1).max(OUTPUT_LIMITS.maxRecordIdLength)` now bounds `affectedRequirementIds[*]`, `affectedMilestoneIds[*]`, `verificationGaps[*].requirementId`, top-level `sourceRecordIds[*]`, and `mitigationOptions[*].sourceRecordIds[*]` — one schema, not five independently-maintained checks. `verificationGaps[*].category`/`assumptions[*]`/`unknowns[*]` each gained their own explicit `.max()`. All existing array-count limits (`maxAffectedIds`, `maxVerificationGaps`, `maxAssumptions`, `maxUnknowns`, `maxSourceRecordIds`, `maxOptionSourceRecordIds`) unchanged. Oversized output fails structural validation outright — nothing is ever silently truncated.
**OpenAI schema compatibility, researched not assumed:** fetched OpenAI's current Structured Outputs documentation and a corroborating community report directly (not relied on training-data recall for a security-relevant claim) — confirmed `minLength`/`maxLength` are **not** part of OpenAI Structured Outputs' supported strict-mode subset (unlike `minItems`/`maxItems`/`pattern`/`minimum`/`maximum`, which the existing `openai-schema.ts` design already assumed worked and which this pass did not re-investigate, being out of this narrowly-scoped correction's remit). Since sending an unenforced length constraint would misrepresent what the provider-facing schema actually guarantees, added `stripUnsupportedStringLengthConstraints()` to `openai-schema.ts`, called on the generated schema before `assertOpenAiCompatibleJsonSchema()` — removes `minLength`/`maxLength` recursively, leaving every other keyword (including the ones the existing disallowed-keyword check already governs) untouched. The authoritative Zod `.min()`/`.max()` runtime checks are completely unaffected; `IMPACT_ANALYSIS_MAX_OUTPUT_TOKENS` (above) is the provider-level size ceiling in place of a schema-level one. No second, hand-maintained output schema was introduced — `impactAnalysisOutputSchema` remains the single source of truth, `buildOpenAiImpactAnalysisJsonSchema()` still derives from it via `z.toJSONSchema()`.
Alternatives: leave `minLength`/`maxLength` in the generated schema on the theory that an unsupported keyword is silently ignored by the API rather than actively harmful (rejected — even if true, it asserts a guarantee to a reader of the generated schema that doesn't actually hold, which is itself the kind of misleading-but-technically-harmless state this project's own documentation discipline exists to avoid); switch to a different structured-output mechanism that does support length constraints (rejected — far outside this narrowly-scoped pass, and the existing `store: false`/strict-JSON-schema design is otherwise sound).

**4. `MAX_PROVIDER_OUTPUT_BYTES = 65,536` — total provider-output size ceiling.** A new pre-validation guard in `validateProviderOutput()` (`packages/core/src/ai/validate-provider-output.ts`), checked _before_ `impactAnalysisOutputSchema.safeParse()` ever runs. `measureProviderOutputBytes()` safely `JSON.stringify()`s the raw output inside a try/catch (never throws — a circular structure, or the small set of inputs `JSON.stringify()` itself returns `undefined` for, both resolve to "could not be measured," treated identically to "too large") and measures the UTF-8 byte length. Oversized or unmeasurable output is rejected as `INVALID_OUTPUT_SCHEMA` with one fixed, safe message — never including the raw output itself. Used directly inside `validateProviderOutput()`, so orchestration (`orchestrator.ts`'s `runProviderAndValidate()`, which already delegates to this function) and the mock evaluation suite (`evals/scenarios.ts`, which calls the identical function) both inherit the guard automatically — no separate integration step needed anywhere.

**5. Semantic-validation errors no longer echo provider-controlled values.** `validateImpactAnalysisSemantics()` (`packages/core/src/ai/output-validation.ts`) previously interpolated the invalid ID and, for a duplicate-citation error, the mitigation option's own provider-generated `title` directly into the returned error string (e.g. `` `sourceRecordIds cites "${id}", which is not...` ``, `` `Mitigation option "${option.title}" cites...` ``) — a confirmed defect, since these strings are both persisted (`ImpactAnalysis.validationErrors`) and fed back to the provider as retry guidance (`LLMProviderRequest.validationFeedback`), meaning a hallucinated or adversarial value could round-trip into permanent storage and into the very next prompt sent to the same (possibly compromised or malfunctioning) provider. Every message now describes only a field path and/or array index — e.g. `"sourceRecordIds[2] is not in the supplied evidence allowlist."`, `"mitigationOptions[1].sourceRecordIds[0] is not in the supplied evidence allowlist."`, `"mitigationOptions[0] has duplicate sourceRecordIds entries."` — using `.forEach((item, index) => ...)` in place of the previous plain `for...of` loops specifically so every message has an index available. The deterministic-equality messages (`scheduleExposureDays`/`budgetExposureAmount`) also dropped the embedded numeric values on the same principle — the provider's claimed figure is still provider-controlled even though it's short and numeric; the field name alone is enough for a human to look both values up directly from persisted deterministic data.

**6. Bounded validation feedback — `sanitizeProviderValidationErrors()`.** A new shared sanitizer (`packages/core/src/ai/validate-provider-output.ts`) applied to every error list `validateProviderOutput()` returns (both the `INVALID_OUTPUT_SCHEMA` and `SEMANTIC_VALIDATION_FAILED` paths, including the new byte-ceiling rejection's own single-element list) — caps the array to `MAX_VALIDATION_ERROR_COUNT` (20), each individual message to `MAX_VALIDATION_ERROR_LENGTH` (240 characters), and the total serialized size to `MAX_VALIDATION_FEEDBACK_BYTES` (4096 bytes), three independent composable bounds rather than one "pick one" limit. Deliberately never truncates mid-string in a way that could leave a fragment of a provider-controlled value behind — by design this never needs to, since fix (5) above already ensures no message contains provider-controlled text in the first place; the length cap here is defense-in-depth, not the redaction mechanism itself. Used automatically by every consumer of `validateProviderOutput()`'s return value (`ImpactAnalysis.validationErrors` persistence, retry `validationFeedback`, any returned safe diagnostic, evaluation reporting) with no separate call needed at any of those call sites.

**Test/documentation fallout from the redaction fix (5):** two existing test assertions in `output-validation.test.ts` and one in `evals/scenarios.ts` (its `invalid-source-id` scenario) previously asserted the fabricated ID _was_ present in the returned errors — now rewritten to assert the opposite (the fabricated value/option title is absent, and the safe path-based message is present instead), since the old assertions directly contradicted the fix. This is corrective, not a weakening: the new assertions are strictly stronger (they verify both a positive — the safe message exists — and a negative — the unsafe one doesn't).

## 2026-07-27 (Phase 6 correction pass) — Provider-terminal-state and validation-error safety

Three confirmed defects, fixed together (the first two are both instances of the same underlying gap — "a piece of provider-controlled content that isn't the JSON payload itself was still trusted"): a response's completion state was checked too narrowly, structural Zod errors still forwarded provider-controlled text, and the SDK's own request/response logging was never explicitly disabled.

**1. Only a genuinely `completed` response is ever eligible for JSON parsing.** The prior check asked one narrow question — "is this specifically an `incomplete` response truncated by `max_output_tokens`?" — and silently let every other non-completed state (a `content_filter`-truncated response, a `failed`/`cancelled`/`in_progress`/`queued` response, an explicit model refusal, or simply an `undefined` status) fall through to `JSON.parse(response.output_text)` as though it were a normal success. A `content_filter` incomplete response whose `output_text` happened to already contain syntactically valid JSON (plausible — the model may have produced a partial, well-formed object before being cut off) would have been silently accepted and persisted as a real analysis result.
New `assertOpenAiResponseCompleted(response)` (`packages/core/src/ai/openai-provider.ts`, exported for direct testing) replaces the old narrow check — it is the one gate between the raw SDK response and `JSON.parse()`, and `response.output_text` is read nowhere else in the file. Exact rule, checked in this order:

1. **Explicit refusal** (any `output` item of `type: "message"` whose `content` includes a `type: "refusal"` entry) — checked _before_ looking at `status` at all, since a model can produce a `completed` response whose sole content is a deliberate refusal, not a truncation. Throws `PROVIDER_REFUSAL`.
2. **`status === "completed"`** (and no refusal found) — returns normally; only this path ever reaches `JSON.parse()`.
3. **`status === "incomplete"`, `incomplete_details.reason === "max_output_tokens"`** — throws `INCOMPLETE_OUTPUT` (retryable — a shorter response on retry may fit within the same ceiling).
4. **`status === "incomplete"`, `incomplete_details.reason === "content_filter"`** — throws `PROVIDER_REFUSAL` (non-retryable — a content-policy block is a property of the request itself, not a transient condition; retrying spends another call for the identical outcome).
5. **`status === "incomplete"` with an absent or unrecognized reason** — a genuine anomaly with no specific handling. **Decision: retryable**, classified as `TRANSIENT_PROVIDER_FAILURE`. Reasoning: an unrecognized reason is more likely a provider-side quirk (e.g. a new reason value this application hasn't been updated to recognize yet) than a permanent, request-specific block, and the cost of guessing wrong is bounded by the orchestrator's existing 2-attempt cap either way — at most one wasted retry, never an unbounded loop.
6. **Any other status** (`failed`, `cancelled`, `in_progress`, `queued`, or anything else, including `undefined`) — throws a fixed, safe `TRANSIENT_PROVIDER_FAILURE`. Deliberately does not special-case `undefined` as "probably an old/incomplete test fake, treat as fine" — a real API response always sets `status`; an `undefined` value is exactly the under-specified shape this gate exists to reject. Every existing test fake's "success" response literal was updated to explicitly include `status: "completed"` and `incomplete_details: null` (and, where the refusal check needed real data, `output: []`) — see `packages/core/src/ai/openai-provider.test.ts`'s `buildFakeClient()` and `orchestrator-provider-spend.test.ts`'s fake `responses.create` implementations.
   None of the six branches ever include `response.error`, `response.output_text`, `response.incomplete_details`, or the refusal text itself in a thrown message — every thrown `AiProviderError` carries only a fixed, category-appropriate string.

**2. New `PROVIDER_REFUSAL` category** (`packages/core/src/ai/errors.ts`), added to `AI_ERROR_CATEGORIES`, deliberately **excluded** from `RETRYABLE_CATEGORIES`. The provider remains structurally incapable of creating options, decisions, or mutations from a refused/incomplete response regardless of retryability — this category only controls whether the orchestrator's second attempt fires, never anything about approval/mutation authority (unchanged from every other category).

**3. Structural Zod-validation errors no longer forward `issue.message`.** Confirmed defect: `summarizeOutputSchemaErrors()` built each returned string as `` `${issue.path.join(".")}: ${issue.message}` `` — and Zod's own default message for an `unrecognized_keys` issue is `Unrecognized key: "<the actual key name>"`, meaning a provider (or a prompt-injection attempt reflected through one) could use nothing but a well-chosen _extra property name_ — no value needed — to inject arbitrary text into `ImpactAnalysis.validationErrors` (persisted) and the next attempt's `validationFeedback` (fed directly back into the live prompt). This is the same class of leak the prior correction pass closed for semantic-validation errors (`output-validation.ts`), left open here because structural (Zod) and semantic (hand-written) validation are two independent code paths.
Fixed: `summarizeOutputSchemaErrors()` now calls a new `summarizeStructuralIssue(issue: z.core.$ZodIssue)` that builds every message from `issue.code`, `issue.path` (rendered as `a.b[2].c` via a new `formatIssuePath()`, matching `output-validation.ts`'s existing path-based style), and schema-authored numeric/enum metadata only (`.minimum`/`.maximum`/`.values` — all of these are _this schema's own_ limits, safe by construction, never anything the provider supplied) — **never** `issue.message`, `issue.input`, `issue.keys`, a received enum value, or any other provider-controlled field. `unrecognized_keys` in particular reports only `"<path>: unexpected fields are not allowed."`, never the offending key name(s). A small `KNOWN_CUSTOM_ISSUE_MESSAGES` map (keyed by path) covers the schema's one `.refine()`-produced `"custom"`-code issue (`mitigationOptions`'s exactly-one-recommended check) with its own fixed, safe message; any other unexpected `"custom"` issue (none currently possible, but not assumed impossible) falls back to a generic `"<path>: value failed validation."` rather than ever reading `issue.message`. Verified empirically (not assumed) which fields each Zod 4.4.3 issue code actually carries before designing this — `unrecognized_keys` has `.keys`/`.path`/`.message` only, `invalid_value` (enum mismatch) has `.values` (the _allowed_ set, not the received value) and no received-value field at all, `too_small`/`too_big` have `.origin`/`.minimum`|`.maximum`/`.exact`, `invalid_format` has `.format`/`.pattern` — no issue code in this schema's actual usage exposes a raw received value or an `issue.input` field, but the formatter never relies on that continuing to hold in a future Zod version, since it never reads `issue.message` regardless of what it might contain.

**4. `sanitizeProviderValidationErrors()` now bounds the _true_ serialized byte size.** Confirmed defect: the prior implementation summed each raw string's own `Buffer.byteLength(error, "utf8")` and compared that running total to `MAX_VALIDATION_FEEDBACK_BYTES` — but the value actually persisted (`ImpactAnalysis.validationErrors`, a JSON column) and actually transmitted (inline in a retried prompt) is `JSON.stringify(errors)`, not the concatenation of the raw strings. `JSON.stringify` adds structural overhead (`[`, `]`, one `,` per separator, two `"` per string) and can _expand_ a string's own byte count further through escape sequences (`"` → `\"`, `\` → `\\`, a literal newline → `\n`, etc.) — summing raw bytes alone silently undercounts both, so a list that looked safely under the ceiling by the old measurement could still exceed it once actually serialized, especially for messages containing quotes, backslashes, or control characters. Fixed: each candidate error is now appended to a _copy_ of the in-progress result array, and the addition is accepted only if `Buffer.byteLength(JSON.stringify([...result, candidateError]), "utf8") <= MAX_VALIDATION_FEEDBACK_BYTES` — the exact same computation a caller would run to measure the real, final array. `MAX_VALIDATION_ERROR_COUNT`/`MAX_VALIDATION_ERROR_LENGTH`/`MAX_VALIDATION_FEEDBACK_BYTES` themselves are unchanged; only how the third bound is measured changed.

**5. SDK request/response logging forced off, cannot be overridden by `OPENAI_LOG`.** The OpenAI SDK's own `debug`/`info` log levels print full request and response bodies to stdout/stderr — including the prompt (which embeds `untrustedData`) and the model's raw output — and by default resolve from `process.env.OPENAI_LOG`, meaning an operator or deployment environment setting `OPENAI_LOG=debug` for an unrelated reason (general SDK troubleshooting, a shared team convention, a copy-pasted `.env` from another project) would silently start logging prompts and model output through this specific provider with zero code change and no warning anywhere in this application. New `OPENAI_SDK_LOG_LEVEL = "off"` constant, included in `buildOpenAiClientOptions()`'s returned `ClientOptions` as `logLevel: "off"`. Verified directly against the SDK's own source (`node_modules/openai/src/client.ts`) that the client constructor resolves `logLevel` as `options.logLevel ?? readEnv('OPENAI_LOG') ?? 'warn'` — the explicit client option is checked _first_, so passing it always wins regardless of what `OPENAI_LOG` is set to; confirmed with a test that sets `process.env.OPENAI_LOG = "debug"` immediately before constructing a real client from `buildOpenAiClientOptions()` and asserts the resolved `client.logLevel` is still `"off"` (restored in `afterEach`, never left mutated for other tests). A companion test confirms the SDK's own real, unconfigured default differs (`"debug"` when `OPENAI_LOG=debug` and no client option is given), proving the override is load-bearing rather than coincidentally redundant with an already-safe default.

**OpenAI Structured Outputs `minLength`/`maxLength` wording corrected.** The prior pass's documentation stated flatly that OpenAI's Structured Outputs strict mode does not support `minLength`/`maxLength` "for every model," as an unqualified universal fact. OpenAI's current documentation describes these (and related type-specific keywords) as additionally called out as unsupported for fine-tuned models specifically, within its broader "some type-specific keywords are not yet supported" guidance — a narrower and more model-dependent statement than this repository's prior wording implied. This repository's own behavior is unchanged: `openai-schema.ts` continues to strip `minLength`/`maxLength` unconditionally from the provider-facing generated schema, for every model, as a deliberately conservative compatibility choice — not because every model is confirmed to reject them, but because the authoritative enforcement is the runtime Zod schema regardless (backed by `IMPACT_ANALYSIS_MAX_OUTPUT_TOKENS` as the provider-level size ceiling), so there is no benefit to a model-specific carve-out and real risk in guessing wrong about which models tolerate the unenforced keywords. ## 2026-07-28 (Phase 7) — Digital-thread graph and read-only MCP server

**Node/edge kind → Prisma relationship mapping, and the reuse-vs-invent tradeoff.** `docs/SPEC.md` §7/§15 fixed the node-kind and edge-kind vocabularies but not which edge kind represents which of the 16 required relationships. Chose a mapping where structural containment (`Program → Component`, `Program → Supplier`, and — reused a second time — `AnalysisRun → MitigationOption`) uses `CONTAINS`; the fallback "no natural parent" links `connectOrphans()` adds also reuse `ASSOCIATED_WITH` rather than inventing a 17th kind for an edge case. Alternatives considered: a strictly 1:1 kind-to-relationship mapping (rejected — the vocabulary has 16 kinds for 16 required relationships plus citations and the orphan fallback, so a 1:1 mapping is arithmetically impossible without either adding kinds beyond the fixed list or reusing at least one) and inventing new kinds for the fallback cases (rejected — `docs/SPEC.md` §4 fixes the edge-kind vocabulary; reuse keeps it closed).

**Orphan connectivity via one generic BFS pass, not per-relationship special-casing.** §5's last sentence ("Program-level records with no natural parent link to the Program node so nothing is orphaned") could have been implemented by hand-checking each optional relationship (`Risk.componentId`, `BudgetItem.componentId`, a `Requirement` with zero `RequirementComponent` rows, a `TestCase` with zero `TestRequirement` rows, a `Defect` with a null `relatedTestCaseId`, …) — instead, `GraphBuilder.connectOrphans()` runs one BFS from the `PROGRAM` node over the already-built edge set (treated as undirected for reachability purposes only) after every other node/edge has been added, and adds an `ASSOCIATED_WITH` edge from `PROGRAM` to anything BFS didn't reach. This is provably complete (a node either has a path to `PROGRAM` through real relationships or it doesn't) and immune to a future new optional relationship being added to the schema without a matching special case being added here.

**Citation representation reuses `SourceReference.wasCited` as-written by the Phase 4 analysis pipeline — no new query logic invented.** `buildAttemptSourceReferenceSnapshot()` (Phase 4) already writes one `SourceReference` row per supplied evidence item with `wasCited` set correctly once a successful response passes validation; `buildProgramThread()` simply reads `wasCited: true` rows for a run's terminal `SUCCEEDED` attempt and turns each into a `CITED` edge (or, for `recordType: "DEPENDENCY"`, `cited: true` metadata on the matching `DEPENDS_ON` edge, since dependencies have no node of their own — see §5). A citation whose target record type has no corresponding node kind, or whose target node was for some reason not built, increments `omittedCitationCount` on the `ANALYSIS_RUN` node rather than being silently dropped or crashing the build.

**Deterministic layout: fixed column table, not dagre/ELK.** `docs/SPEC.md` explicitly permitted adding a layout library "unless the deterministic native layout proves materially inadequate." A hand-rolled column-per-kind + sorted-row-within-column scheme was sufficient for this program's size (dozens of nodes, not thousands) and kept the layout pure/dependency-free/directly unit-testable without a rendering environment. Revisit if a much larger seeded program is ever introduced.

**Client bundle must never import a runtime value from `@missionthread/core`'s root barrel.** Discovered via manual dev-server verification, not a theoretical concern: `thread-layout.ts` originally did `import { THREAD_NODE_KINDS, ... } from "@missionthread/core"`, and because it's transitively imported by the `"use client"` `thread-graph.tsx`, Next's Turbopack tried to bundle `@missionthread/core`'s root barrel — which also re-exports `./db` (`@prisma/client` + `pg`) — into the browser, and failed with `Module not found: Can't resolve 'tls'`/`'util/types'` (Node built-ins `pg` needs, absent in a browser bundle). Fixed by switching every client-bundled file under `apps/web/.../thread/` to `import type` only for anything sourced from `@missionthread/core`, and deriving `thread-layout.ts`'s internal kind-order map from its own local `COLUMN_BY_KIND` object instead of importing the `THREAD_NODE_KINDS` runtime array. This is the same class of issue Phase 5's Playwright database-isolation repair hit from the server side (a narrow subpath export avoiding eager Prisma construction) — here the fix is "don't import a runtime value that eagerly pulls Prisma in at all," since there's no subpath re-export that would help a client bundle avoid `./db` specifically while still getting `THREAD_NODE_KINDS`.

**MCP SDK: stable v1 (1.30.0), stdio only, `McpServer`/`registerTool` — the current high-level API, not the deprecated `.tool()` overloads.** `registerTool(name, config, callback)` accepts either a `ZodRawShapeCompat` (a raw per-field shape) or a full `AnySchema` (a `z3`/`z4` schema object) as `inputSchema` — chose the latter so `packages/core/src/mcp/schemas.ts`'s existing `.strict()` `z.object({...})` schemas (already shared with each service's own internal `safeParse()` call) could be passed directly to `registerTool()` with no duplicate raw-shape definition to keep in sync. Verified empirically that the SDK independently rejects an unrecognized input field at the protocol layer (before the tool handler ever runs) when given a `.strict()` object schema this way.

**MCP server build: esbuild bundle of this package's own source _and_ `@missionthread/core`'s source, not a plain `tsc` emit.** `packages/core/src/**/*.ts` uses extensionless relative imports (`from "./db"`, not `from "./db.js"`) under TypeScript's `moduleResolution: "bundler"` — valid for every other consumer in this monorepo (Next.js/Turbopack, Vitest/esbuild), all of which tolerate omitted extensions, but **not** loadable by plain Node ESM, which requires an explicit extension on every relative specifier. A `tsc`-emitted `dist/index.js` that `import`s `@missionthread/core` (whose `package.json` `exports` field points straight at `./src/index.ts`) would fail at runtime with `Cannot find module '.../src/db'` the moment Node tried to resolve `packages/core`'s own extensionless imports — confirmed directly (see the "manually verified" note below) before choosing the fix, not assumed. Chose `esbuild --bundle`, inlining both packages' own source into one self-contained `dist/index.js` (resolved at build time, not runtime — esbuild's resolver, unlike Node's, tolerates the same extensionless imports every other tool in this repo already does) while marking every genuine npm dependency (`@prisma/client`, `@prisma/adapter-pg`, `pg`, `openai`, `@modelcontextprotocol/sdk`, `zod`) `external` so they're still resolved normally from `node_modules` at runtime — `@prisma/client` specifically cannot be bundled, since it dynamically loads a native query-engine binary. Alternatives considered: rewriting every relative import across `packages/core` to carry an explicit `.js` extension (rejected — a large, invasive, high-blast-radius change to a package five other phases' worth of code and tests already depend on, far outside Phase 7's scope, for a problem `packages/mcp-server`'s own build step can solve unilaterally); running the built server via `tsx`/`ts-node` instead of a real build (rejected — `docs/SPEC.md` explicitly asked for "a real emitted build for the production start command"). `packages/mcp-server/tsconfig.json`'s `moduleResolution` was correspondingly changed from the placeholder's original `NodeNext` to `bundler` (matching `packages/core`'s own tsconfig) — `NodeNext`'s strict extension requirement made `tsc --noEmit` itself unable to resolve `@missionthread/core`'s types at all, independent of the separate runtime-bundling question.

**Manually verified, not assumed:** before choosing the bundling fix, ran the actual failure directly (`node -e 'import("@missionthread/core")...'` → `Cannot find module '.../src/db'`), then confirmed the fix by building `dist/index.js`, spawning it as a real child process via the MCP SDK's own `StdioClientTransport`, and completing a live `initialize` → `tools/list` → `tools/call get_program_summary` round trip against the real seeded database.

## 2026-08-01 (Phase 8) — Screenshot capture tool and demo script

`docs/SPEC.md` §19's Phase 8 scope lists "diagrams/screenshots/demo script" as one deliverable. Two additions:

**`scripts/capture-screenshots.mjs`** (new root `npm run docs:screenshots`) — a permanent, reusable dev tool (not a one-off scratch script, and not part of any test suite or CI step) that signs in as the seeded Program Manager against a server the operator has already started, and captures nine PNGs of the main authenticated surfaces (login, dashboard, program overview, event-entry form, digital-thread graph, analysis workspace, readiness briefing, decision page, audit) to `docs/assets/screenshots/`. Two design choices worth recording:

- Uses `page.goto(url, { waitUntil: "domcontentloaded" })` plus a short fixed settle delay, never `waitForLoadState("networkidle")`. A first version used `networkidle` throughout and hung indefinitely partway through the run in this environment — cause not fully isolated (this app has no known long-lived polling/streaming connection today), but `networkidle` has no bound of its own against any future page that adds one (a live status poll, an SSE connection), and a documentation tool that can hang forever is worse than one that reliably takes a slightly-early screenshot. `page.setDefaultTimeout(15_000)` is also set explicitly so no single action can hang the whole script regardless.
- The seeded analysis run's link is discovered from the digital-thread graph page's accessible fallback list (`a[href^="/programs/edgelink-x/analyses/"]`), not the program overview page — the overview page's "Recent events" section only ever renders an **Analyze** trigger, never a link to an already-completed analysis; the graph page's fallback list is where `build-program-thread.ts` actually places that link (see the 2026-07-29 Phase 7 correction-pass entry above). Finding it this way, rather than hardcoding a seed ID, means the script has no seed-ID knowledge to go stale.

**`docs/DEMO_SCRIPT.md`** — a ~10-minute guided walkthrough of the full protected workflow spine (event → deterministic analysis → bounded AI interpretation → three mitigation options → approval → apply preview → audit), written for a human presenter, not a script to execute. It deliberately records a new event and applies a real change rather than only viewing the pristine seeded fixture, so a presenter can show the live create-analyze-approve-apply-audit path, not just a pre-baked example — and says so explicitly, with the reset command (`npm run db:seed:dev:destructive`) to restore the pristine seed afterward. Cross-checked against `apps/web/e2e/decision-workflow.spec.ts` (the same flow, scripted) so every step described is already independently, automatically verified — this document narrates existing, tested behavior, it doesn't assert new behavior of its own.

README.md gained a "Screenshots" section (image grid plus the regeneration command) and a pointer to `docs/DEMO_SCRIPT.md` from "Project status."
